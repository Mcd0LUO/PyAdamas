# 归纳变量强度削减（IVSR）：为什么在 PyAdamas 上是负优化

> 状态：**已实现、已实测、已回退**。代码不保留，结论保留。
> 日期：2026-11-17　对应提交区间：0.265 之后

## 一句话结论

把循环内的 `j*7` 换成每轮 `+= 7` 的累加器，在 nbody 上让 `advance`
从 1006 行涨到 **1929 行**（+92%），**运行时间退步 15.7%**。

原因是收益模型算错了：**被消掉的乘法只有 1 条，代价是 12 个累加器**。

## 出发点：Go 确实这么做了

`go tool objdump -s 'main.advance'` 显示 Go 的 nbody advance：

- 41 条 `LEAQ` 在**循环外**预计算所有 `i*7+k` / `j*7+k` 偏移
- 内层循环体里 **0 条 `IMULQ`**
- 221 条指令，单次索引访问 3 条（`CMPQ` / `JBE` / `MOVSD`）

对照 PyAdamas（0.265 之后）：1006 条指令，单次索引访问 9 条，
内层循环每轮都要 `imulq $7` 重算偏移。看起来是明确的机会。

## 实现

`src/opt_loop.cpp` 新增 `strength_reduce_iv_function()`（约 300 行）：

1. **识别自然循环**：回边 = `b -> h` 且 `h` 支配 `b`；循环体从回边来源
   反向可达（不含 `h` 的循环外前驱）构成。
2. **识别归纳变量**：latch 里 `store.slot S, (load.slot S + const)`，且
   header 里 `cmp.lt (load.slot S), LIMIT`。
3. **识别副本槽**：降级器会把 `j` 同时存进 `s13`（循环变量）和 `s7`
   （体内副本），乘法读的是 `s7`。只认 `s13` 会漏掉全部候选。
4. **改写**：为每个 `iv * K` 建累加 vreg，前置块初始化 `acc = iv_init * K`，
   latch 里 `acc += step * K`，循环体内所有读改成读 `acc`。

## 根因分析

### 1. 被消掉的乘法只有 1 条

统计 nbody 内层循环 `bb10`（114 条 IR 行）的乘法：

```
bb10: int mul = 1   (j*7)
      float mul = 16  (业务逻辑，无法消除)
```

整个内层循环里**只有 1 条整型乘法**值得削。

### 2. 代价是 12 个累加器

IVSR 实际匹配到的是**外层**循环（`i` 循环），因为 `i*7` 在它的循环体里
出现 12 次（内层循环的每次索引访问）。于是：

- 前置块插入 12 条 `acc = i_init * K`
- **latch 插入 12 条 `acc += step*K`**，而该 latch 每轮执行
- 12 个新 vreg 参与寄存器分配，把内层循环的浮点值挤出 xmm8-15

实测 `advance` 从 1006 行涨到 1929 行（+92%），栈访问 `movsd` 从 27 处
涨到 70 处。

### 3. 收益模型错在哪

IVSR 的正确收益模型是：

```
收益 = 乘法次数 × 循环执行次数  -  累加更新次数 × latch 执行次数
```

在 nbody 里：

- `i*7` 在外层循环体里**每轮只算 1 次**（进入内层循环前）
- 累加器在外层 latch 里**每轮更新 1 次**
- 两者次数相同 ⇒ 乘法换成加法本身**零收益**（`imul` 和 `add` 同为 1 uop）
- 但额外引入 12 个 vreg ⇒ 寄存器压力上升 ⇒ **净亏**

IVSR 只在「乘法的**使用次数**远多于累加更新次数」时才划算，典型场景是
`a[i]` 这类**单层循环内的直接索引**。nbody 是三层嵌套循环，外层归纳
变量的乘法只被用一次（内层循环的索引基址），不满足条件。

## 如果要做，正确的做法是什么

### 方案 A：只对最内层循环做，且要求 K > 1 且乘法被多次使用

nbody 最内层循环（`j`）里 `j*7` 只出现 1 次，削掉它省 1 条 `imul`，
但要加 1 个累加器 + 1 条 `add`。**零收益**。所以 nbody 本身不适合 IVSR。

### 方案 B：把偏移折进寻址模式（真正的 Go 做法）

Go 不是在循环里维护累加器，而是**把 `i*7+k` 预计算成 7 个独立偏移**，
循环内用 `MOVSD 0(AX)(CX*8)` 的单条寻址。PyAdamas 的 `index.get` 是
一个完整的 IR 指令（带边界检查），无法表达「基址+偏移」的复合寻址。

要拿到 Go 的收益，需要：

1. IR 支持「带偏移的索引」（`index.get base[idx+const]`）
2. codegen 把它编成 `movsd off(data,idx,8)`
3. 归纳变量本身留在寄存器里（当前 `list` 是堆类型，被排除出寄存器分配）

第 3 条是硬约束：GC 靠帧记录里的栈槽地址找根，提升到寄存器后栈槽不
更新会让对象被提前回收（ASan 实测过 SEGV）。需要先有栈映射。

### 方案 C：索引算术外提（只提不变量，不建累加器）

`i*7` 在外层循环体里是**循环不变量**（只依赖外层归纳变量 `i`，在内层
循环里不变）。现有 LICM 没有提出它，因为 LICM 的判据是「在 header 处
已定义且循环内无重定义」—— `i*7` 定义在外层循环体里，对内层循环而言
确实是 header 支配的，理论上可以提。

**这是唯一可能有效的方向**，但需要检查 LICM 为什么没提（可能是
`bin.mul` 的操作数 `%32 = load.slot s7` 是槽读，LICM 对槽读有额外限制）。

## 教训

「Go 这么做」不等于「这么做有收益」。必须先把**收益模型**写下来并代入
实测数字验证，否则容易把「减少了一条乘法」误当成「循环变快了」。

这次的关键失误是：看到 Go 内层循环 0 条 `IMULQ` 就认为 IVSR 有收益，
没有先数「PyAdamas 内层循环有几条乘法值得削」—— 答案是 1 条。
## 方案 C 的实测结论：也不成立

补测了「让现有 LICM 提出 `i*7`」这条路。结论：**做不到**。

LICM 的 `hoistable` 判据里，`Bin` 要求两个操作数都 `operand_ok`。`i*7` 的
操作数是 `%32 = load.slot s7`，而 `s7` 在**内层循环体内被写过**：

```
bb10 (for.body):
  %24 = load.slot s13   ; j
  store.slot s7, %24    ; s7 = j   <-- 内层循环内写
  %32 = load.slot s7
  %34 = bin.mul %32, %33  ; j * 7
```

`slot_written[s7] = true` ⇒ `LoadSlot s7` 不可提升 ⇒ 依赖它的 `bin.mul`
也不可提升。这个判断是**正确的**：`s7` 每轮都变，提到循环外会算错。

要让方案 C 成立，必须先让降级器不产生「循环变量副本槽」（直接读 `s13`），
那是 lower 层的改动，且会牵动其他依赖副本槽的优化。不在本轮范围。

## 最终判断

nbody 内层循环的 `j*7` 是**单条**整型乘法，而它所在的循环每轮要做 16 条
浮点乘法 + 24 次带检查的索引访问。削掉 1 条整型乘法（换成 1 条加法）
对总时间的贡献在噪声级别，任何额外开销（多一个 vreg、多一条 spill）
都会把它吃掉。

**PyAdamas 要缩小与 Go 在 nbody 上的差距（3.36x），只能靠：**

1. 边界检查消除（实测上界 -7.3%，当前已拿到 -4.0%）
2. 堆槽提升 + 栈映射（消掉每次索引访问的基址重载）
3. IR 支持复合寻址 `base[idx+const]`（Go 的 `MOVSD 0(AX)(CX*8)`）

归纳变量强度削减不在这个列表里。
