# 全局寄存器分配 —— 设计

状态：**实现中**。本文记录为什么需要它、现有后端的天花板在哪、以及分几步落地。

## 现状与瓶颈

后端目前**没有真正的寄存器分配**：变量（槽位）默认全部落在栈上，
只有两类局部优化把它们搬进寄存器：

1. **整函数常驻**（`assign_slot_regs`）：按访问频次挑前 N 个槽，整函数常驻在
   callee-saved 寄存器里。池是 **6 个**（`rbx` `r12`–`r15` `rbp`）。
2. **块内借用**（`assign_block_temp_regs`）：整块没有调用指令时，把 `r8`–`r11`
   借给**块内临时值**（vreg），块结束全部归还。不覆盖跨块变量。

浮点另有 8 个常驻池（`xmm8`–`xmm15`），但只在「无调用的整型/浮点函数」里用。

### 实测天花板

`bench/compare/matmul.py`（`__pa_main` 里的三重循环）：

| 指标 | 数值 |
|---|---|
| 栈访问（`load.slot`/`store.slot`） | 44 处 |
| 总 `(%rsp)` 访问 | **120 处** |
| 6 个 callee 寄存器 | 全部用满 |
| 性能 | 16 ms（Go 2.7 ms，**5.9×**） |

**关键**：`matmul` 内层循环里**没有任何调用**，那 4 个 scratch 寄存器
（`r8`–`r11`）本可以借给变量用，但现在只借给块内临时值，跨块的循环变量
拿不到。同时活跃变量有 7 个（`i k j aik` + `a b c` 基址），6 个 callee 寄存器
无论如何都不够 —— **排序不是瓶颈，池大小和「能不能借 caller-saved」才是**。

### 为什么以前不能借 caller-saved

`r8`–`r11` 是 caller-saved：任何 `call` 都会破坏它们。所以变量要常驻在这些
寄存器里，必须在**每个调用点**做保存/恢复，或者只在「不跨调用」的区间里用。

后者正是块内借用做的事 —— 但它要求「整块无调用」，条件太严，覆盖不到
「循环体内有调用、但循环变量跨迭代活着」这种最常见的情形。

## 目标与范围

**目标**：给槽位（变量）做**基于活跃区间**的分配，允许跨块复用寄存器，
并在调用点按活跃性决定保存/恢复。

**不在本次范围**：
- 不做 SSA 形式的分配（IR 已经是三地址码 + 可变槽，改动太大）
- 不做指令调度、不做强度削减
- 不改浮点池的既有逻辑（先做整型）

## 分步落地

### R1：活跃性分析（基础）

对**槽位**（不是 vreg）做块级 live-in / live-out 数据流，位图表示。
`build_fp_liveness` 已经是这个形状的模板（只跟踪提升过的浮点槽），
推广到全部整型槽即可。

**验收**：加一个 `PYADAMAS_RA_DEBUG=1` 环境变量，dump 每个块的 live-in/out，
人工核对几个简单函数。

### R2：线性扫描分配（callee 池）

按活跃区间起点排序，线性扫描分配 `rbx`/`r12`–`r15`/`rbp`。
溢出（区间多于寄存器）时选**最长区间**溢出到栈槽。

相比现在的「按频次挑前 N 个」，线性扫描能让**不同时刻**的变量复用同一寄存器，
显著提高覆盖率。

**验收**：`__pa_main` 的 `(%rsp)` 访问数下降；205 个用例全过。

### R3：调用点保存/恢复（caller 池）

把 `r8`–`r11` 也纳入分配池，但在**每个调用点**：

- 调用前把「活跃且当前在 caller-saved 寄存器里」的值 store 到栈槽
- 调用后 load 回来

这是「caller-saved 的代价」，但只要活跃值不多，比全程走栈便宜。

**验收**：`matmul` / `nbody` / `spectral_norm` 三个基准的差距缩小；
栈访问数明显下降。

### R4：与现有机制的交互（必须一起验证）

这些是**已知的耦合点**，改动时必须逐条确认：

1. **帧记录与 GC**：帧记录登记的是**栈槽地址**，GC 按地址读值。
   变量提升到寄存器后，栈槽里是旧值 —— GC 会读到过期的指针。
   现有代码用 `ir_is_heap` 挡掉了堆槽，但**R3 之后 caller-saved 里的值
   在调用点会写回栈槽**，要保证写回时机早于可能触发 GC 的调用。
2. **异常展开**：`pa_frame_unwind` 按帧记录释放堆引用。寄存器里的值
   不在记录里，展开时会漏释放。现有代码用 `has_handlers` 降级处理，
   Z5 之后非可挂起函数不再有 setjmp，但**表驱动展开仍然逐帧走 personality**，
   需要重新审视这个门禁。
3. **长跳转回滚**：setjmp/longjmp 会把 callee-saved 恢复到 setjmp 时刻。
   生成器/协程仍然走 setjmp，所以它们的 callee-saved 用法要维持现状。
4. **`SlotAddr`（取地址）**：一旦取过地址，该槽不能再提升 —— 现有逻辑
   已经用 `addr_taken` 挡掉，保持不变。

## 度量方法

改动前后必须用同一套指标对比，不能只看「感觉快了」：

```bash
# 栈访问数（编译期指标，最直接）
./build/release/pyadamas asm bench/compare/matmul.py | grep -cE 'load\.slot|store\.slot'

# 真实性能（四语言基准）
python3 bench/compare/run_compare.py --repeat 5 matmul nbody spectral_norm
```

回归门槛：205 个运行用例 + 五套异常夹具 + 差分测试全过。

## 已否决的方案

- **只做循环深度加权**（试过，已回退）：槽位 load/store 数 47 → 47，
  性能无变化。原因是 `matmul` 活跃变量 7 个而池只有 6 个，
  **排序无法解决数量不足**。
- **全量 tag / NaN-boxing**：与本次无关，且已在 roadmap 明确不做。
