# 包管理设计先验（PyAdamas）

> 状态：**设计研究**，不含实现、不改 `src/`。所有「候选设计」是待拍板的提案，不是承诺。
> 不确定的外部事实标 **（待核实）**；每条外部结论都给了 URL（见附录 A）。
> 现状事实都给了 `文件:行`（见附录 B），可以逐条复核。

一句话：**PyAdamas 的包管理不是「把东西装进运行环境」，而是「把依赖图钉死，然后让编译器把整张图编成一个二进制」**。

## TL;DR（六个结论）

| # | 结论 | 一句话理由 |
|---|---|---|
| 1 | 包在**运行期不存在**：`import` 是编译期别名，没有 `sys.modules`、没有运行期模块对象 | 所以 pip/npm 里「装到环境里」的那一半机制整体不适用（§1.3） |
| 2 | 解析用 **MVS（最小版本选择）**，不用 SAT/回溯 | 解析结果只依赖清单，可预测、可解释、无 NP 难；编译型语言的成本大头在编译不在解析（§5.2） |
| 3 | 缓存用**全局内容寻址 store + 项目侧只存解析结果**（pnpm 模式），分源码与编译产物两级 | 这才是「包共用缓存」的正确形态；项目里不存在 `node_modules` 式物化树（§5.4） |
| 4 | 多版本立场：**默认单版本，显式别名才允许不兼容 major 并存，绝不静默共存** | 符号可以版本化（编译型语言的礼物），但同名类型跨版本 = 两个类型，自动共存会把解析问题变成类型系统问题（§5.3） |
| 5 | 锁文件是**唯一构建真相**，构建默认 `--locked`；只有 `update` 能写锁 | 消灭「清单说一套、锁文件另一套」这类漂移（§5.5、§4） |
| 6 | 分六阶段：P0 锁+路径依赖 → P1 源缓存+离线 → P2 注册表+MVS → P3 产物缓存 → P4 多版本 → P5 治理 | 每阶段都可独立验收；P3 的键设计必须为 P4 预埋版本（§6） |

## 1. 问题陈述：PyAdamas 的「包管理」到底要解决什么

### 1.1 先把模型前提钉死（三条，都有代码证据）

| # | 前提 | 证据 | 对包管理的含义 |
|---|---|---|---|
| P-1 | **没有运行期模块对象**：`import m` 只是编译期别名，`from m import x` 是快照绑定；没有 `sys.modules`、没有 `getattr(module, ...)`、没有运行期名字表 | [language.md](language.md#L833-L846)；[architecture.md](architecture.md)「只借语法，不背兼容包袱」 | 运行期不存在「加载哪个版本」的问题——**所有版本决策必须在编译前完成** |
| P-2 | **每个程序独立编译、静态链接成一个二进制**：链接 = 全部 `mod.o` + `rt.o` + `-lm -ldl`；没有 `.so`/`.a` 发布物，没有跨包 ABI 承诺 | `driver_build.cpp:981-1019`（`link_program`） | 「安装」没有意义；**「获取 + 编译」就是构建的一部分**。反过来，没有 ABI 面意味着包可以只发源码（与 Conan/vcpkg 根本不同） |
| P-3 | **模块边界 = 二进制接口文件 `.pya`**：导入方只读接口、不读对方 AST；跨模块符号是 `pyadamas$<module>$g$<name>` 这类 mangled 名 | `module.h:1-5`、`module.h:41-55`（`interface_hash`、`kModuleFormatVersion=12`、`kModuleAbiVersion=1`）、`module.cpp:458-489` | 包管理的产物是**源码 + 接口 + `.o`**；**模块名就是符号前缀**，所以「同一个包的两个版本」在符号层面必然冲突——这是编译型语言特有的、pip/npm 永远不会遇到的问题 |

由此得到本文的核心判断：**PyAdamas 的「环境」不是一块共享可变的磁盘区域，而是「一次构建的模块图 + 它的输入」**。包管理器要做的是：把这张图**确定地**算出来（解析）、把输入**完整地**取到本地（获取/缓存）、让编译器**只**按这张图编译（集成）、把输入**可验证地**钉死（锁定/信任）。

### 1.2 需求分解

| 需求 | 通用包管理器里的形态 | PyAdamas 里的形态 | 必需性 | 关键差异 |
|---|---|---|---|---|
| 依赖声明 | `pyproject.toml` / `package.json` 里的名字+范围 | 同样的清单，但声明的是**编译期模块图的输入**（包坐标 + 可选别名 + 模块映射） | 必需 | 声明必须能表达「这个包提供哪些可 import 的顶层模块」 |
| 解析 | 选版本、解冲突（回溯/SAT/MVS） | 同样，但结果必须是一张**模块名唯一的 DAG**，且跨包符号不冲突 | 必需 | 失败发生在编译前；错误必须能指到「谁要求了什么」 |
| 获取 | 下载 wheel/tarball/source | 下载**源码树**（可选预编译产物缓存） | 必需 | 不需要「构建好的 wheel」，因为构建器就是编译器本身 |
| 缓存 | `~/.cache/pip`、pnpm store、ccache | **内容寻址 store**：源码树 + 编译产物（`.o`/`.pya`/清单）两级 | 必需且更重要 | 每次构建都要编译，缓存收益远大于「装好就不用编」的生态 |
| 构建集成 | wheel 已构建 / Node 无需构建 | **模块图合并、符号命名、接口文件生成、链接、缓存失效** | 必需且是主要工作量 | 包管理器与编译器必须共同设计，不能只做外围工具 |
| 可复现 | lockfile + hash | lock + **工具链固定** + **产物里不能有绝对路径** | 必需且更难 | 现状 `.pya` 里嵌了绝对 `source_path`（`module.cpp:498`），这一条现在**不成立** |
| 供应链信任 | 哈希、签名、SBOM、审计 | 同样的机制，但**哈希是主证据**（编译发生在自己机器上，发布者只发源码） | 必需（分阶段） | 没有运行期，所以没有「运行期校验」这一层；签名只解决「谁发布」 |

### 1.3 在「编译期解决一切」下**根本不需要**的东西

这一节是本文最重要的减法。每一条都给出「为什么不需要」和「硬搬会怎样」。

| 机制 | pip/npm 为什么需要它 | PyAdamas 为什么不需要 | 硬搬会怎样 |
|---|---|---|---|
| **运行期包加载**（`require()`、`importlib`、动态 import 解析） | 解释器要在运行时按名字找模块、建模块对象 | 没有运行期模块对象（P-1），`import` 在编译期就消解成符号引用 | 会在一个「没有名字表」的语言里重新引入名字表，直接违背架构的核心取舍 |
| **install / postinstall / `build.rs` 式安装期脚本** | 需要「装的时候」编译原生扩展、下载二进制、打补丁 | **没有「安装」这一步**：获取是取源码，构建是编译器的工作 | 安装期任意代码执行 = 把最大的一类供应链风险请回来（§2.8、§4.5） |
| **虚拟环境 / 解释器隔离** | 多个项目共享一个 site-packages，必须隔离 | 每个程序是自包含二进制，没有共享运行环境 | 会引入「环境是可变全局状态」的全部毛病（§2.7），而收益为零 |
| **运行期版本探测 / 特性探测**（`hasattr`、`if pkg.__version__`） | 动态语言靠运行时判断能力 | 静态类型 + 无内省，能力在编译期就确定 | 需要在运行期保留元数据，与「没有名字表」冲突 |
| **跨包 ABI 兼容矩阵**（so 版本、dll、binding redirect） | 预编译二进制要能互相链接 | 每次从源码重建整张图，没有跨包 ABI 面 | 会逼我们维护「二进制兼容」承诺，而当前模型恰好可以不做 |
| **入口点 / console_scripts** | 解释器要 dispatch 到 Python 函数 | 要发命令就直接发二进制（可选，非 P0） | 引入运行期解释器依赖 |
| **命名空间包**（`pkgutil.extend_path`） | 运行期拼 `__path__` | 源码级目录 + `__init__.py` 已足够（`driver_modules.cpp:37-79`） | 无必要复杂度 |

### 1.4 反而**更需要**的五件事

| 需求 | 为什么在 PyAdamas 里更重 | 现状证据 |
|---|---|---|
| **编译产物缓存** | 没有「装好就固定」的二进制，每次构建都要重新生成 `.o`；依赖一多，构建时间线性上涨 | 已有 per-module 缓存（`driver_build.cpp:581-625`），但键是「模块名 + 源路径」、目录在**编译期常量** `build/<build>/modcache` 下、工具链用 mtime 识别（`driver_build.cpp:132-153`）→ **不能跨项目/跨机器共享** |
| **符号命名冲突** | 模块名就是符号前缀（P-3）：两个版本 = 两套同名符号 = 链接期重复定义 | `module.cpp:466`：`pyadamas$<module>$g$<name>`；`sanitize_symbol` 是**有损**的（非字母数字→`_`，`driver_modules.cpp:15-21`） |
| **全程序模块图合并** | 包不是独立编译单元：导入方要读全部依赖接口；图必须是 DAG | 已有循环导入检测（`driver_build.cpp:373-381`）与拓扑序（`p.order`） |
| **类型身份** | 跨版本同名类 = 两个不同类型，必须在编译期诊断而不是运行期怪错 | `ImportedClass` 带 `origin_module`/`qualname`（`module.h:19-25`、`driver_build.cpp:795-808`） |
| **锁文件是「输入」而不是「安装记录」** | 编译不确定源（绝对路径进接口、工具链 mtime 进缓存键）让可复现比 Python 更难 | `.pya` 编码含绝对 `source_path`（`module.cpp:498`）→ 换目录即接口哈希变 |

### 1.5 与 pip/npm 模型的结构差异（一张表）

| 维度 | pip / npm | PyAdamas（候选） |
|---|---|---|
| 「环境」是什么 | 共享、可变、可被手工污染的一块磁盘区域 | 一次构建的**模块图 + 输入集合**，纯函数 |
| 「安装」是什么 | 把包解到环境里（可能执行脚本） | 把源码取进 store（**不执行任何代码**） |
| 依赖在何时解析 | 安装时（并可能再次在运行时） | **编译前一次**，结果写进锁文件 |
| 冲突表现 | 安装报错 / 运行期 ImportError / 版本混用 | **编译期**类型错误或解析错误 |
| 版本混用的手段 | 隔离环境、嵌套 node_modules | 符号版本化 + 显式别名 + 类型身份（§5.3） |
| 复用的单位 | 包（解包后的目录） | 内容（源码树哈希、编译键） |

### 2.1 展开：钻石依赖为什么是「单值名字空间」的必然

把问题抽象掉语言细节：设包 `C` 被 `A` 要求 `>=1.0`、被 `B` 要求 `>=1.2`。若「C」这个名字在一次构建里只能指向一个实体，那么：

- 选 `1.2` → 满足双方（MVS 的答案，单调、无需回溯）；
- 若 `A` 要求 `<2.0`、`B` 要求 `>=2.0` → **不存在**同时满足的实体。此时只有三种出路：改要求（人决策）、让名字分裂成两个（多版本）、失败。

关键洞察：**「冲突」不是版本范围的错，而是「一个名字一个实体」的错**。pip/npm 的复杂性（回溯、SAT、错误解释）本质是在「名字必须单值」的约束下做约束求解。MVS 的做法是**放弃「满足所有上界」这个目标**，只保留下界并取最大——于是永远有解、永远单调、永远可解释（§5.2）。上界需求用「人显式覆盖」或「名字分裂」来满足，而不是交给求解器。

### 2.2 展开：幽灵依赖的机制（为什么 PyAdamas 现在就有）

Node 的解析算法是「从当前文件目录逐级向上找 `node_modules/<name>`」，配合 hoisting 把传递依赖提到根，于是**没写进 package.json 的包也能 import 成功**——解析规则比声明规则宽松，这就是幽灵依赖。

PyAdamas 现状更直接：`resolve_module_path`（`driver_modules.cpp:37-79`）的搜索根依次是「导入方目录 → 用户 `-I` → 从导入方父目录一路向上到 `/` → stdlib」。这意味着：

- 任何上层目录里一个 `json.py` 都会改变解析结果（**环境相关**）；
- 同一个名字解析到两个不同文件时会直接报错（`driver_build.cpp:487-494`），但**「该不该被解析到」没有声明可查**；
- 内置 native 模块不可被劫持（`driver_modules.cpp:191-207`），但纯 Python 源 stdlib 模块**可以**被用户文件覆盖——这是有意的兼容行为，也是「解析规则 ≠ 声明规则」的现成例子。

结论：包管理必须把「包模块的解析」从**路径搜索**改成**查表**（§5.6 的 ModuleMap）。一旦查表，「未声明 = 不存在」就是免费的严格性。

### 2.3 展开：锁漂移的三种典型形态

| 形态 | 怎么发生 | 为什么危险 | 我们的对策 |
|---|---|---|---|
| 隐式重写 | `install` 发现清单与锁不一致，顺手改锁（npm 的默认行为之一） | 锁不再是「审阅过的输入」，而是「工具的最新意见」 | 构建**只读**锁；写锁只发生在 `update`/`resolve` 显式命令 |
| 多工具多格式 | 同一生态多个工具各自写锁（npm/yarn/pnpm 的 lock 格式互不兼容） | 团队里谁跑哪个命令，锁就变一次 | 锁格式由**一个**实现定义，且给出版本号与稳定序列化 |
| 环境相关字段 | 锁里写入本机路径、时间、平台特有内容 | 换机器锁就变 → 要么频繁冲突，要么有人手动改 | 锁里**禁止**绝对路径/时间/环境变量；平台差异用显式字段表达 |

### 2.4 展开：install script 为什么是「设计上可避免」而不是「靠纪律避免」

npm 的 install 脚本之所以危险，是因为**「安装」这个动作本身需要一个执行者**：要编译原生模块、要下载二进制、要打补丁，于是给了包作者一个「在用户机器上执行代码」的入口，而且这个入口对**传递依赖**同样开放。

PyAdamas 没有这个动作：获取 = 把源码树放进 store（纯数据），构建 = 编译器读源码产出 `.o`（唯一的执行者是编译器，且它不执行包提供的任何代码）。因此「不做 install script」不是一条纪律，而是**模型推论**——除非有人主动把「包可以提供构建脚本」加进来，否则这个攻击面不存在。这条优势应当写进设计不变量，防止未来「为了方便」破例（比如允许包提供「生成代码」的脚本）。

## 3. 先行者调研：机制层面对照

调研的判据只有两条：**这个机制在我们这个「编译期解决一切」的模型里能不能搬**，以及**它踩过的坑我们会不会踩**。所以每一节都给「可借鉴 / 要避免」两列，最后给一句结论。

### 3.0 总表

| 系统 | 一句话结论 | 最该学的机制 | 最该避开的机制 |
|---|---|---|---|
| NuGet | 把「解析后的图」做成一等构建输入是对的；版本语义含糊与两代清单模型是历史债 | `project.assets.json`（图即输入）、CPM 的仓库级单版本、transitive pinning 的显式覆盖 | 裸版本号 = 最低适用、restore 隐式联网改文件、`packages.config` 与 `PackageReference` 长期并存 |
| pnpm | 与我们的目标形态最接近：全局内容寻址 store + 项目侧只有引用 | 内容寻址 + 硬链接、严格布局（无幽灵依赖）、`store prune` 的可达性 GC | peer 依赖的组合爆炸（我们不需要）、依赖符号链接语义（我们连树都不物化） |
| npm / yarn | `node_modules` 是**运行期解析结构**，不是构建产物目录；把它搬进编译型语言必然水土不服 | Yarn PnP 的「解析表 + 内容缓存、不物化树」 | hoisting、嵌套树、install 脚本 |
| Cargo | semver 兼容就合并、不兼容就并存，是务实的中间路线；但 feature 并集是隐形坑 | lockfile + checksum、同 major 合并、`[patch]` 显式覆盖 | feature 全局并集、`build.rs` 任意构建期代码、`*` 版本要求 |
| Go modules | **最值得学的对象**：MVS 的可预测性 + 主版本进路径 + 内容哈希校验 | MVS、`go.sum`、`/v2` 路径、vendor 一致性检查、`retract` | 只有下界导致「下界声明不准」要靠工具/纪律兜底 |
| pip / poetry / uv | 回溯求解的代价主要是**可解释性**和**时间**；uv 证明「全局缓存 + 项目侧极薄」能大幅提速 | 锁带哈希、`--locked/--frozen/--offline`、把缓存当不可信的心态、硬链接复用 | 回溯求解、把环境当可变全局状态、无哈希的 `requirements.txt` |
| Deno / 浏览器 ESM | 「解析结果 = 标识符→坐标 的一张表」是对的（import map）；「完全没有版本约束」不行 | import map 作为解析表、URL 级内容身份、lock 记完整性 | 无版本代数（升级全靠手改）、把 URL 直接写进源码 |
| Nix | 内容寻址 + 封闭输入是可复现的最高标准；但门槛与「一个世界一个版本」是反面教材 | 哈希为唯一真相、输入封闭、二进制缓存按内容复用 | 需要学一门语言/重写构建系统、nixpkgs 单体（单版本到极致） |
| C/C++ 系 | **与我们最像的一类**：编译型、无运行期模块、符号在链接期定生死 | 二进制缓存键 = 兼容性元组（Conan `package_id`）、baseline 快照（vcpkg）、action cache（Bazel）、哈希钉死（Zig/FetchContent） | recipe/port/构建脚本即代码（任意执行）、无解析层（FetchContent）、无上界导致 major 破坏 |

### 3.1 NuGet

NuGet 是「包管理 + 构建集成」耦合最深的先行者，也是**版本语义最容易让人误解**的一个。

| 机制 | 它怎么做 | 可借鉴 | 要避免 |
|---|---|---|---|
| 版本范围 | `1.0` 表示「最低适用」（`>=1.0`），`[1.0]` 才是精确，`[1.0,2.0)` 是区间，`2.8.*` 是浮动 | 区间/精确/浮动三种语义都有人需要 | **裸版本号 = 下界**极易被读成「锁死」，是长期误用源；我们应强制写运算符（§5.1） |
| 解析规则 | 「最低适用版本」「浮动版本」「直接依赖优先（direct-dependency-wins）」「同层依赖（cousin dependencies）」 | 「直接依赖优先」是显式覆盖的雏形 | 四条规则互相作用，人是很难预测结果的——这正是我们选 MVS 的反例 |
| 还原产物 | restore 在内存里解出图，然后写 `project.assets.json`；构建读这个文件 | **图是一等产物、构建只读图**——我们的锁文件 + 模块解析表就是这个位置（§5.5/§5.6） | 把「还原」做成构建的隐式副作用（联网、改文件） |
| `packages.config` vs `PackageReference` | 旧模型把**含传递依赖的扁平列表**写进 `packages.config`，安装即改项目文件、无传递解析；新模型由 restore 传递解析，支持 per-TFM 资产 | 新模型的「声明与解析分离」是对的 | 两代清单模型长期并存 → 工具矩阵爆炸、迁移痛苦。**我们只做一代**（§4.6） |
| 传递依赖固定（transitive pinning） | 在 CPM 下把传递依赖隐式提升为顶层 pin；文档明确「transitive pinning 时不允许降级」 | 给「我想覆盖某个传递依赖」一个**显式、可审计**的入口 | 隐式提升会让「清单里没写的东西」也有版本决策，可读性差 |
| Central Package Management | 仓库根 `Directory.Packages.props` 统一版本，项目只写引用 | **仓库级单版本**对应用型仓库非常好用（对应我们的 workspace 场景，§7-Q9） | 中央文件与项目文件又是一层漂移面 |
| 多目标框架 | 同一项目对不同 TFM 可有不同资产/版本，assets 文件按 TFM 分区 | 「同一份声明、多套解析结果」的结构（对应我们「同图不同 target/flags 的编译键」） | 组合数爆炸 |

**结论：学「解析后的图 = 构建输入」与「仓库级单版本 + 显式 pin」；避开「裸版本号即下界」的语义含糊、两代清单并存、以及把还原做成隐式副作用。**

来源：<https://learn.microsoft.com/en-us/nuget/concepts/dependency-resolution>（四条规则、assets 文件）、<https://learn.microsoft.com/en-us/nuget/consume-packages/central-package-management>（CPM、transitive pinning）。`packages.config` 的官方页面本轮抓取 404（已归档/迁移），细节**待核实**。

### 3.2 pnpm

pnpm 是我们**缓存模型**的直接原型。它的两句口号正好对应我们的两个痛点：内容寻址解决「重复安装/磁盘膨胀」，严格布局解决「幽灵依赖」。

| 机制 | 它怎么做 | 可借鉴 | 要避免 |
|---|---|---|---|
| 内容寻址 store | 文件按内容哈希存进全局 store；`node_modules` 里每个文件都是 store 的**硬链接**；版本升级只新增变化的文件 | 全局共享、文件级去重、天然免疫「半写坏」以外的重复 | 文件级去重会带来大量小文件与硬链接上限问题——我们先做**包级/树级**寻址，文件级去重作为后续可选优化（§5.4） |
| 严格布局 | 根 `node_modules` 只放**直接依赖**的软链；真实文件在 `.pnpm/<pkg>@<ver>/node_modules/<pkg>` | 「项目侧只有引用，实体在 store」正是我们要的形状 | `.pnpm` 仍是 per-project 物化目录（只是软链）——我们可以做到**完全不物化**（§5.6 ModuleMap） |
| 禁止幽灵依赖 | 未声明的包在根看不到 → import 直接失败 | 严格 deps 的实证：宽松解析不是「方便」而是「负债」 | — |
| `node-linker` | `isolated`（默认）/`hoisted`/`pnp` 三种物化策略 | 承认「布局」是可插拔的实现细节，不是语义 | 选项越多，生态越难兼容（大量工具假设 `node_modules` 存在） |
| `store prune` | 删除「没有被系统上任何项目引用」的包 | **GC = 全局可达性**（roots = 各项目 lock），不是 LRU | 需要「项目登记表」才能可靠算 roots；没有登记表就只能保守不删（§5.4） |
| peer 依赖 | 用哈希后缀把不同 peer 组合区分成不同实例 | 「同一版本 + 不同上下文 = 不同实体」的思想，将来若做 feature/配置时可能用到 | peer 组合爆炸是 pnpm 最复杂的部分（我们当前不需要） |

**结论：学「全局内容寻址 store + 项目侧只有引用 + 可达性 GC + 严格 deps」；避开把项目侧物化成目录树、以及 peer/组合语义的复杂度。**

来源：<https://pnpm.io/motivation>（CAS、硬链接、非扁平布局）、<https://pnpm.io/symlinked-node-modules-structure>（`.pnpm` 布局）、<https://pnpm.io/cli/store>（`prune` 语义）。`node-linker` 选项细节与「pnpm 10 默认阻止生命周期脚本」**待核实**（相关页面本轮未取到）。

### 3.3 npm / yarn

这一节的教训是**否定式**的：`node_modules` 之所以成为「上帝包管理灾难」，是因为它同时承担了三个角色——依赖存储、解析结构、运行期查找表。编译型语言只需要第一个。

| 机制 | 它怎么做 | 可借鉴 | 要避免 |
|---|---|---|---|
| hoisting / 扁平化 | 把所有依赖尽量提到根，靠 semver 兼容性去重；解析时沿目录向上找 | — | **幽灵依赖的根源**；结果依赖安装历史与顺序；去重是启发式而非声明 |
| 嵌套回退 | 版本不兼容时在包内部再放一份 `node_modules` | 用「位置」编码「版本」的土办法，证明多版本共存有真实需求 | 树深不可控、路径长度上限、重复体积 |
| lockfile v1/v2/v3 | 从「依赖名→版本」树到「路径→包」表；不同版本字段不同 | 锁必须能重建**完整图**而不只是直接依赖 | 格式随大版本变化、跨工具不兼容 |
| Yarn PnP | 不生成 `node_modules`；把 `(包, 发起者)→位置` 的解析表写进 `.pnp.cjs`；缓存是 zip；`zero-installs` 可把缓存提交进仓库 | **最接近我们的目标**：解析表 + 内容缓存，不物化树；严格性（未声明依赖报错） | `.pnp.cjs` 是运行期补丁（我们要的是编译期表）；`zero-installs` 会让仓库膨胀；生态兼容代价大 |
| install 脚本 | `preinstall`/`install`/`postinstall` 默认执行 | — | 供应链最大攻击面（§2.8） |

**结论：学 PnP 的「解析表 + 内容缓存、不物化树」；把 `node_modules` 这种「一套结构干三件事」的做法整体排除。**

来源：<https://yarnpkg.com/features/pnp>（无 `node_modules`、ghost dependency protection、shared installs、zero-installs）。npm 的 hoisting 没有权威规范（实现细节），本文按社区共识描述；`lockfileVersion` 差异**待核实**到具体版本号。

### 3.4 Cargo

Cargo 是「务实中间路线」的代表：**兼容就合并，不兼容就并存**。它对我们的价值在于把「多版本共存」的代价说清楚了。

| 机制 | 它怎么做 | 可借鉴 | 要避免 |
|---|---|---|---|
| 版本要求与统一 | 默认 caret（`^1.2.3`）；SemVer 兼容的版本**统一成一个**；不兼容 major 允许多份并存 | 「同 major 合并、跨 major 并存」正是我们要借鉴的分界线（§5.3） | 并存后「同名不同类型」无法互传，用户容易困惑——所以我们要求**显式别名**才允许并存 |
| `Cargo.lock` | 全图 + 校验和；二进制提交、库不提交 | 锁记全图（含传递依赖）+ checksum | 「库不提交锁」导致下游解析结果不同（对我们是灾难：编译型项目的复现性更敏感） |
| feature 统一 | 整个图对同一 crate 的 feature 取**并集**（additive）；resolver v2 修了部分过度统一 | feature 是「加能力」的干净模型 | **并集是隐形的全局状态**：某个依赖开了 feature，你的构建行为就变了；我们应避免隐式并集（§7-Q3） |
| `-Z minimal-versions` | 强制解析到最低兼容版本，用来验证「声明下界是否真实」 | 说明**下界声明不可靠是生态问题**，需要工具定期体检（对应我们的 `update --check-lower-bounds`） | 需要 nightly；说明这条路没成为默认 |
| `cargo vendor` + source replacement | 把依赖源码 vendor 进仓库，改 source 指向本地目录；`--offline` | 离线/内网的成熟做法：**vendor 是 store 的一个子集，且必须可校验** | vendor 目录与锁漂移（需要一致性检查） |
| `[patch]` / `[replace]` | 在清单里显式改写某个依赖的来源 | **显式覆盖**的正确入口（对应我们的 override） | 覆盖过多会让锁失去意义 |
| `build.rs` | 构建期执行任意 Rust 代码 | — | 与 install script 同类风险；**我们不做**（§4.5） |

**结论：学「同 major 合并 + 全图锁 + 显式覆盖 + vendor 校验」；避开 feature 隐式并集与任何构建期脚本。**

来源：<https://doc.rust-lang.org/cargo/reference/resolver.html>（SemVer 统一/冲突报错）、<https://doc.rust-lang.org/cargo/guide/cargo-toml-vs-cargo-lock.html>（锁的作用与可复现）、<https://doc.rust-lang.org/cargo/reference/features.html>（feature 统一与 resolver v2 的修正）、<https://doc.rust-lang.org/nightly/cargo/reference/unstable.html>（`minimal-versions`）、<https://doc.rust-lang.org/cargo/commands/cargo-vendor.html>（vendor/offline）。

### 3.5 Go modules

Go 是**最值得整套借鉴**的对象：它把「可预测的解析」做成了算法性质，而不是工程约定。

| 机制 | 它怎么做 | 可借鉴 | 要避免 |
|---|---|---|---|
| MVS（最小版本选择） | 每个模块的要求是一个**最低版本**；最终选中版本 = 所有要求里的**最大值**；不做回溯，闭包一遍算完 | **核心借鉴**：单调、唯一不动点、O(N)、结果只依赖清单（注册表后来发版不影响已有构建） | 没有上界 → 需要靠「添加依赖时写最新版本」+ `go mod tidy` 的纪律兜底 |
| 主版本进路径 | 不兼容演进 = 换 import path（`example.com/lib/v2`） | **多版本共存的干净解**：不同路径 = 不同模块 = 不同类型，天然无冲突；我们的「版本进 mangling」是同一思想（§5.3/§5.6） | 源码里的 import 路径会随 major 变（迁移成本），但换来的是「同一构建里两份 v1/v2 完全合法」 |
| `go.sum` | 记录模块内容（zip）与 `go.mod` 的哈希；校验和不匹配即失败 | **完整性锚点与版本解耦**：版本给人看，哈希给机器验 | 与 `go.mod` 两个文件两份真相（我们合成一个锁文件，§5.5） |
| proxy 与校验库 | `GOPROXY`（逗号分隔、`direct`/`off`）、`GOSUMDB` | 源可替换、可离线、多镜像回退 | 默认联网 + 校验库依赖中心服务（内网要额外配置） |
| vendor | `go mod vendor` + `vendor/modules.txt`；`go>=1.14` 且一致时自动用 vendor | **一致性检查**：vendor 与 go.mod 不一致就报错，而不是静默用过期的 vendor | 仓库里多一份源码（体积） |
| `retract` | 声明某版本撤回，但已锁定的构建仍可用 | 撤回语义：**不重写历史** | — |

**结论：整套借鉴 MVS + 主版本进标识 + 内容哈希 + vendor 一致性；只有「没有上界」这一点需要用显式 override/别名补上，而不是靠求解器。**

来源：<https://go.dev/ref/mod>（模块/版本/校验/vendor 的规范）、<https://research.swtch.com/vgo-mvs>（MVS 的设计动机：可预测、避免「任意细粒度控制顶层构建」）。

### 3.6 pip / poetry / uv

这一类的价值是**反例 + 缓存设计**：回溯求解的代价被 Python 生态完整地展示了一遍；uv 则展示了「全局缓存 + 薄项目侧」能带来什么。

| 机制 | 它怎么做 | 可借鉴 | 要避免 |
|---|---|---|---|
| 回溯求解 | pip 20.3 起支持回溯：先假设版本，发现不满足就回退重选；冲突时报「ResolutionImpossible」并给因果链 | 冲突解释的**消息结构**值得学（谁要求了什么） | 最坏指数级；社区大量「解析太慢/太深」的案例；结果依赖注册表当前状态 |
| 隔离单位 | venv：每个项目一个环境目录 | 「项目级隔离」这个需求本身是对的 | **环境是可变全局状态**：手工 `pip install`、卸载残留、多个 venv 互相污染；我们没有运行环境，正好不需要它 |
| 锁 | poetry.lock（含 hashes）；`install --sync`；requirements.txt + `--require-hashes` 才算完整锁 | 锁必须带哈希与全图 | 无哈希的 `==` 列表是「假锁」 |
| uv 缓存 | Rust 实现，全局缓存 + 硬链接/reflink 到各 venv；`--locked/--frozen/--offline`；`uv cache prune`；文档有 cache safety 一节（缓存应按不可信处理） | **全局缓存 + 项目侧极薄 + 显式离线模式**；「缓存不可信、读时校验」的心态 | 仍需快速求解器（我们不需要：MVS 就够） |

**结论：学「全局缓存 + 薄项目侧 + 锁带哈希 + 显式离线/锁定模式 + 缓存不可信」；避开回溯求解与「环境即状态」。**

来源：<https://pip.pypa.io/en/stable/topics/dependency-resolution/>（20.3 起回溯、代价）、<https://docs.astral.sh/uv/concepts/cache/>（缓存设计、hardlink/CoW 的空间统计、cache safety）。poetry 与本轮个别细节**待核实**。

### 3.7 Deno / 浏览器 ES modules

这一类回答「如果不要中央版本代数，世界会怎样」：答案是——**身份清晰、升级原始**。

| 机制 | 它怎么做 | 可借鉴 | 要避免 |
|---|---|---|---|
| URL 即标识 | `import "https://host/x@v/mod.ts"`；一个 URL 就是一个模块，缓存按 URL | 身份 = 坐标，简单直接；多版本 = 不同 URL，天然共存 | 没有版本约束/范围 → 升级要手改所有 import；URL 写进源码 → 换镜像要全改 |
| import map | 把裸标识符映射到 URL（支持 scopes：不同子图不同映射） | **解析结果就是一张表**——正是我们 ModuleMap/锁文件的形状（§5.6） | map 只是重映射，不含版本求解；表与代码的一致性靠工具 |
| 完整性 | `deno.lock` 记录依赖 URL 的完整性哈希 | 锁记录「内容」而不只是「坐标」 | 早期无 lock，可复现性靠 URL 不可变（**待核实**当前细节） |
| 浏览器 | import maps 是唯一标准化的重映射；实际解析由 CDN 在服务端做 | 说明「解析」可以完全是构建/服务端的职责 | 浏览器没有包管理器 → 每个站点自己拼 CDN 版本 |

**结论：学「解析结果 = 标识符→坐标 的表 + 内容完整性」；避开「完全没有版本代数」和「坐标泄漏进源码」。**

来源：<https://docs.deno.com/runtime/fundamentals/modules/>（URL specifier、`importMap`/`--import-map`、管理依赖的章节）。`deno.lock` 的具体字段**待核实**。

### 3.8 Nix

Nix 是可复现性的**上界**：它把「构建 = 输入内容的纯函数」推到极致。我们要学它的**输入封闭**，但不要学它的**世界模型**。

| 机制 | 它怎么做 | 可借鉴 | 要避免 |
|---|---|---|---|
| derivation | 一个 derivation 描述「输入（store path + 哈希）→ 构建命令 → 输出 store path」 | **构建键 = 全部输入**——我们的编译键设计直接照这个思路（§5.4） | 需要一个「纯函数式」的构建语言/求值模型 |
| 内容寻址 store | 所有输入输出都在 store 里，路径由内容/输入决定；二进制缓存按 store path 复用 | 共享缓存 = 派生对象复用，不是「装过的包列表」 | store path 泄漏进产物（调试信息里的绝对路径）会破坏复现——我们的 `.pya` 已经有这个病（`module.cpp:498`） |
| 封闭构建 | 沙箱、无网络、固定输入 | **默认离线构建**（§5.7） | — |
| flake.lock | 按内容哈希钉住输入（nixpkgs 到 commit、依赖到 nar hash） | **锁钉内容哈希而不是版本号**（§5.5） | 需要 flake 概念与额外工具链 |
| 为什么难用 | 要学 Nix 语言/lazy 求值/模块系统；报错晦涩；`nixpkgs` 单体「一个世界一个版本」；glibc/工具链一变就大规模重建（没有 ABI 缓冲）；非确定性构建要打补丁 | 反面教材：**中心化单版本 + 无 ABI 缓冲 = 全量重建**，这正是我们要避免的「上帝包管理」的 Nix 变体 | 重学一门语言；重写整个构建系统；`nixpkgs` 式的「全世界一套版本」 |

**结论：学「哈希为唯一真相 + 输入封闭 + 缓存按内容复用」；避开「必须学一门语言/重写构建系统」的门槛与「一个世界一个版本」的单体模型。**

来源：<https://nix.dev/manual/nix/latest/language/derivations>（derivation 的输入→输出结构）。content-addressed derivation、flake.lock 字段、store path 泄漏的细节**待核实**（相关页面本轮未取到）。

### 3.9 C/C++ 系：Conan / vcpkg / FetchContent / Bazel / Zig（**与本项目最像**）

先说根因：**C/C++ 的依赖地狱不是包管理器的锅，是「符号只带链接名、不带版本」这件事的锅。**

| 现象 | 根因 | PyAdamas 的对应物 | 我们能不能解 |
|---|---|---|---|
| ODR 违规 | 同一符号在多个 TU 有不同定义，链接器只挑一个 | 模块名就是符号前缀（`pyadamas$<module>$...`），两个版本会产生同名符号 | 能：**版本进 mangling**（§5.6） |
| ABI 不兼容 | C++ 没有稳定 ABI；`std::string` 布局、异常、RTTI 都能变 | 我们没有跨包 ABI：每次从源码重建整张图 | 不需要解（这也是「只发源码」的理由） |
| 内联命名空间 | libstdc++ 用 `std::__cxx11` 把新旧 ABI 编进符号名 | 同一个思想：**把不兼容版本编进标识** | 能，而且比 C++ 彻底（连类型身份一起编） |
| dll hell / binding redirect | 运行期只能加载一份 dll，谁覆盖谁赢 | 静态链接 + 一个二进制，没有运行期加载 | 不会中 |

**Conan 2**

| 机制 | 它怎么做 | 可借鉴 | 要避免 |
|---|---|---|---|
| `package_id` | 由 settings（编译器/版本/stdcpp/arch/构建类型）+ options + **依赖的 package_id** 算出二进制身份；相同 id 才能复用预编译包 | **二进制缓存键 = 兼容性元组**——我们的 `.o` 编译键就是同一个东西（§5.4） | 键里有「依赖的 id」→ 依赖一变下游全变（我们没有 ABI，可以只对接口敏感，见 §5.6） |
| 二进制兼容模型 | 声明「哪些不同设置仍可兼容」（如 cppstd 向下兼容），允许复用 | 「兼容性可以显式声明」的思路 | 声明错了就是静默错链接 |
| 版本范围 | 图求解时解析范围（取满足的最高版本），需要 lockfile 才能复现 | 范围 + 锁的组合 | 图求解 + 范围 = 结果依赖注册表状态；我们的 MVS 只保留下界 |
| recipe | `conanfile.py` 是**Python 脚本**：构建逻辑、下载、打补丁都在里面 | 表达力强 | **构建逻辑即代码 = 任意执行 + 不可静态审计**；这是我们要极力避免的（§4.5） |

**vcpkg**

| 机制 | 它怎么做 | 可借鉴 | 要避免 |
|---|---|---|---|
| baseline | 仓库某个 commit 定义「所有 port 的默认版本」；清单只写约束 | **一个快照定义全世界**——对应用型项目极好用（升级 = 刷 baseline，一次全局、可审阅） | baseline 与 port 补丁耦合；无上界遇到 major 破坏靠打补丁兜底 |
| 版本约束 | 只支持 `version>=`（下界），解析成**单一版本** | **没有上界 → 钻石依赖天然不冲突**（与我们选 MVS 同一个理由） | 无法表达「不要 2.x」；只能靠 baseline 回退 |
| triplet | arch/os/crt 链接方式组成 triplet，决定二进制兼容 | 编译键的环境维度 | 组合爆炸 |
| port | CMake 脚本声明依赖与构建 | 声明式依赖（比 recipe 好） | 仍是构建脚本（任意代码） |
| ABI hash 二进制缓存 | 对 port 定义 + 工具链算哈希，命中才复用 | 缓存键要覆盖「构建脚本 + 工具链」 | 哈希算漏一项就静默错（**待核实**具体实现细节） |

**CMake FetchContent（「没有包管理器」的默认结局）**

| 机制 | 它怎么做 | 可借鉴 | 要避免 |
|---|---|---|---|
| configure 期下载 | `FetchContent_Declare(... URL ... URL_HASH ...)` 在 configure 阶段把源码拉下来并 `add_subdirectory` | `URL_HASH` 的「内容钉死」态度 | **没有解析层**：每个子项目各自 `find_package`/`FetchContent` → 钻石依赖只能靠碰巧同名同版本，否则重复或冲突 |
| 无锁 | 指向分支/tag 就不可复现 | — | 完全不可审计；「今天能编明天不能」 |

**这一格是 PyAdamas 的「现状镜像」**：`-I` + 目录搜索 + 每个项目自己决定依赖，就是 FetchContent 的心智模型。它证明「不做解析层」不是省事，而是把冲突推迟到链接期。

**Bazel（bzlmod）**

| 机制 | 它怎么做 | 可借鉴 | 要避免 |
|---|---|---|---|
| 声明/解析/锁分离 | `MODULE.bazel` 声明 → 模块图解析出版本 → `MODULE.bazel.lock` 钉住（含哈希） | **三件事分离**：这几乎就是我们 §5 的骨架 | 两代模型（WORKSPACE / bzlmod）并存的历史包袱 |
| external repo 命名 | 每个外部依赖是一个 repo 名，不同版本 = 不同 repo 名 → **可共存** | 别名/命名空间让多版本共存变简单 | 概念多（repo/package/target） |
| action cache | 远程缓存的键 = 动作的全部输入内容（源文件哈希 + 命令行 + 环境） | **编译键 = 全部输入**的最成熟工程实现（§5.4） | 需要构建系统级别的输入追踪（我们已有 manifest 雏形） |
| 严格 deps | 必须显式声明依赖，否则构建失败 | 无幽灵依赖 | — |

**Zig（`build.zig.zon`）**

| 机制 | 它怎么做 | 可借鉴 | 要避免 |
|---|---|---|---|
| 哈希钉死 | 依赖声明 = URL + 内容哈希；`zig fetch` 负责把哈希写进清单；内容不符直接报错 | **最简模型**：先把「钉死」做对，再谈「求解」（P0/P1 的基线心态） | 没有范围/求解 → 每个升级都要手改，钻石收敛靠人工 |
| 无中央注册表 | 依赖就是 URL，去中心化 | 简单、无运维 | 发现性/审计/信任全靠用户自己 |

**结论：学 Conan 的「二进制缓存键 = 兼容性元组」、vcpkg 的「baseline 快照 + 只有下界」、Bazel 的「声明/解析/锁分离 + action cache」、Zig 的「哈希钉死」；避开「recipe/port/构建脚本即代码」与「没有解析层」。C++ 的符号/ABI 教训直接推出我们的两条设计：版本进 mangling、不发二进制。**

来源：<https://docs.conan.io/2/reference/binary_model/package_id.html>（`package_id` 计算与二进制兼容）、<https://docs.conan.io/2/tutorial/versioning/version_ranges.html>（版本范围）、<https://learn.microsoft.com/en-us/vcpkg/users/versioning>（baseline、`version>=`、版本排序规则）、<https://cmake.org/cmake/help/latest/module/FetchContent.html>（configure 期获取、`URL_HASH`）、<https://bazel.build/external/overview>、<https://bazel.build/external/module>、<https://ziglang.org/learn/build-system/>。Bazel 的版本选择规则、`multiple_version_override`、vcpkg ABI hash、Zig `.zon` 字段细节**待核实**（页面为 JS 渲染或已迁移，本轮未取到正文）。

## 4. 反模式清单：明确写「我们不做」

每一条给四样东西：**我们不做的事**、**为什么**、**替代方案**、**怎么强制**（能靠编译器/工具强制的，绝不靠纪律）。

| # | 不做 | 为什么 | 替代方案 | 怎么强制 |
|---|---|---|---|---|
| 4.1 | **不做运行期包加载** | 没有运行期模块对象/名字表（architecture.md）；引入它等于把解释器请回来 | 编译期解析 + 符号引用 + 静态链接 | 架构上不存在 `sys.modules`/`importlib` |
| 4.2 | **不做隐式全局安装**（无 `-g`、无 PATH 魔法、无「全局装了就到处能用」） | 全局状态污染（§2.7）；「我这跑不了」的头号来源 | store 只按内容存**数据**；「可用」由清单/锁决定，不由「装过」决定 | 构建时只读清单+锁+store；没有「已安装列表」这个概念 |
| 4.3 | **不做无锁的「按范围现场解析」** | 解析结果依赖注册表此刻状态 → 不可复现（§2.5/§2.6） | 锁是唯一真相；默认 `--locked`；`update` 才解析 | 构建命令默认拒绝锁漂移；CI 用 `--locked` |
| 4.4 | **不做嵌套式依赖树** | 每包一份副本 → 重复/膨胀/身份分裂（§2.2/§2.4）；这是 node_modules 灾难的骨架 | 每个程序**一张图**；包之间不嵌套 | 解析结果是 DAG；`deps tree` 是拓扑序而非目录树 |
| 4.5 | **不做 install / build 脚本**（任何「包提供代码在构建期执行」） | 供应链最大攻击面（§2.8）；破坏可审计/可复现（§2.14） | 清单是**纯数据**；要生成代码就让用户在自己的项目里写，编译器不执行包代码 | 清单格式里没有「命令」字段；解析器拒绝未知字段 |
| 4.6 | **不做「清单说一套、锁说另一套」** | 锁漂移（§2.5）；两套真相必有一方过期 | 清单=意图（范围），锁=结果（精确）；不一致 = 错误 + 给出 diff | `--locked` 校验；锁只能由 `resolve/update` 写 |
| 4.7 | **不做可变注册表**（版本内容不可重写） | 供应链与复现的根基：同一坐标必须永远同一内容 | 内容寻址 + 不可变发布；撤回用 `retract` 语义（不删历史） | 下载后校验哈希；哈希不符不写入 store |
| 4.8 | **不做「环境作为状态」**（无 venv 等价物、无 `PYTHONPATH`） | 环境是共享可变状态（§2.7）；我们没有运行环境 | 构建自包含；`-I` 只作为 legacy 逃生口 | 清单项目里包解析只走 ModuleMap；`-I` 只对 legacy/本地模块生效 |
| 4.9 | **不做隐式传递依赖**（幽灵依赖） | 解析规则比声明宽松 = 幽灵依赖（§2.2） | 严格 deps：用到的模块必须由清单可达 | 编译器已经扫 import（`driver_modules.cpp:256-352`）→ 不在 ModuleMap 的包模块直接报错 |
| 4.10 | **不做绝对路径进产物/缓存键** | 换目录/换机器即失效（§2.6）；现状 `.pya` 就带绝对路径（`module.cpp:498`） | store 内用相对/内容路径；接口里只记坐标与逻辑名 | 可复现检查（`--reproducible`）+ 接口格式升级 |
| 4.11 | **不做「多版本静默共存」** | 同名类型跨版本分裂，会把解析问题变成类型问题（§5.3） | 默认单版本；要并存必须**显式别名** | 无别名时遇到 major 分叉 = 明确报错并给三种出路 |
| 4.12 | **不做共享缓存的非原子写 / 无校验读** | 已实测过并发写缓存的风险（`tests/cache_race.sh`）；共享后风险放大 | 临时文件 + 原子 rename；读时校验哈希；用 lease 防 GC 竞态 | store 写入只走原子路径；读校验失败 = 报错而非静默使用 |
| 4.13 | **不做构建期联网** | 不确定性 + 不可审计 + 离线不可用（§2.10） | `fetch`（联网）与 `build`（离线）分离 | 默认离线构建；需要网络时必须显式 `fetch`/`update` |

## 5. 候选设计

### 5.0 七条设计原则（后面每个决策都回指这里）

| # | 原则 | 含义 | 对应反模式 |
|---|---|---|---|
| D-1 | **声明与解析分离** | 清单写意图，解析产出锁；构建只读锁 | 4.3、4.6 |
| D-2 | **身份 = 坐标 + 内容哈希** | 名字只是别名；哈希才是「同一份东西」的证据 | 4.7、4.10 |
| D-3 | **构建输入封闭** | 编译键必须覆盖所有影响产物的输入（编译器、目标、开关、源码、依赖接口/实现） | 4.12、4.10 |
| D-4 | **单一真相** | 任一时刻只有锁（构建期）或清单（更新期）一个权威 | 4.6 |
| D-5 | **不为运行期留后路** | 任何「运行期再想办法」的机制直接排除 | 4.1、4.5 |
| D-6 | **失败必须可解释** | 解析/编译失败要能说清「谁要求了什么、冲突在哪、怎么解」 | 4.11 |
| D-7 | **向后兼容优先** | 没有清单的项目行为不变（legacy 模式）；有清单才启用新机制 | 4.8 |

### 5.1 标识与版本

#### 5.1.1 包坐标

```
坐标     = [ registry "/" ] namespace "/" name "@" version
registry = 主机名（"pyadamas.dev"、"mirror.corp.example"…）或省略（默认注册表）
namespace= 小写标识符，允许 "-"，由注册表分配/拥有
name     = 小写标识符，允许 "-"
version  = MAJOR "." MINOR "." PATCH [ "-" pre ] [ "+" build ]   （semver 2.0.0 子集）

例：pkg-json@1.4.0
    @acme/http-client@2.0.1                       ← 作用域（scoped）写法
    mirror.corp.example/@acme/http-client@2.0.1   ← 显式来源，锁里必须记全
```

（上面的块是**格式草案**，不是实现代码；下同。）

| 属性 | 取值 | 理由 |
|---|---|---|
| 注册表维度 | 是（默认 + 可覆盖） | 内网镜像/私有库是刚需（§5.7）；但默认值让 99% 的写法保持简短 |
| 大小写 | 全小写；禁止仅靠 `-`/`_` 区分两个包 | 避免 Windows/macOS 大小写不敏感文件系统的坑 |
| 包名 vs 模块名 | **包名可以带 `-`，模块名必须是合法标识符**（现状 `valid_module_name`，`driver_modules.cpp:23-28`） | 语言层 `import pkg-name` 不合法；必须在清单里显式映射（§5.1.2） |
| 一个包提供几个模块 | 1..N | 标准库既有 `urllib/__init__.py` 这种包，也有单文件模块；不强行一对一 |
| 版本与内容 | 版本是**语义承诺**，内容哈希是**完整性证据**；锁里两者都记 | 版本给人看/给范围用，哈希给机器验（§5.5） |

#### 5.1.2 包名到模块名的映射

语言的 `import` 只认合法标识符，而包名习惯带 `-`（`pkg-json`）。规则：

| 情形 | 规则 | 例子 |
|---|---|---|
| 包名本身是合法标识符 | 默认提供一个同名顶层模块 | `linalg` → `import linalg` |
| 包名不合法（含 `-`/`.`） | 必须在清单里用 `modules` 表显式映射 | `pkg-json` → `modules = { json = "src/json.py" }`，源码写 `import json` |
| 一个包多个模块 | `modules` 全部列出；子模块用包内相对路径 | `modules = { "http" = "src/http/__init__.py", "http.client" = "src/http/client.py" }` |
| 两个包提供同一模块名 | **错误**（除非其中一个被别名覆盖）；不能靠解析顺序 | 见 §5.9 冲突规则 |
| 保留名 | `_` 开头的顶层模块名、`__entry__`（已保留，`driver_build.cpp:464-468`）、stdlib 内置名 | `import math` 永远指向内置接口，包不能占用 |

为什么不在语言层加语法（比如 `import pkg-json`）：**语法改动会污染语言**，而清单里的映射表是纯数据、可迁移、可丢弃。Python 生态的「包名 ≠ 模块名」已经是既成事实（`beautifulsoup4` → `bs4`），我们把它**显式化**而不是藏起来。

#### 5.1.3 版本语义

| 规则 | 内容 | 类比 |
|---|---|---|
| 格式 | 严格 semver 2.0.0 的一个子集：必须有 `MAJOR.MINOR.PATCH`；pre-release 只允许 `-alpha.N`/`-beta.N`/`-rc.N` 这类可排序形式 | Cargo / Go |
| 比较 | 按 semver 规则（数字段数值比较，pre-release 优先级低于正式版） | — |
| 兼容性 | 清单只允许两种写法：`^1.4.2`（= 下界 `>=1.4.2`，**上界由「major 即身份」天然保证**，不需要范围语法）与 `= 1.4.2`（精确）。**不支持** `~`、`<`、`<=`、裸版本号 | 修正 NuGet 的坑（§3.1）；上界一旦可写，就会重新引入「范围求解」与「上界冲突」 |
| 兼容边界 | `major != 0` 时边界 = major；`major == 0` 时边界 = `0.minor`（0.4 与 0.5 视为不兼容） | Cargo 的 0.x 约定；0.x 没有稳定性承诺 |
| 日期版本 | **不允许**作为主版本形式 | 日期没有「兼容承诺」语义，无法参与范围代数 |
| 任意字符串版本 | 只允许用于 **path / git 依赖**，且必须被哈希钉死；不参与版本比较 | Cargo 的 git 依赖 |
| 跨 major | 不靠版本范围表达「并存」，靠别名（§5.3） | Go 的 `/v2` 思想 |

**为什么不用内容哈希当版本（Nix/Deno 风格）**：

1. 人需要「1.4.0 修了 bug」这种**可比较、可承诺**的语义；纯哈希无法表达「兼容范围」，清单里也就写不出 `^1.4`。
2. 哈希对「还没下载的内容」不可知——解析阶段必须在**下载之前**就选出候选集，纯哈希做不到。
3. 现代生态的升级体验依赖「同 major 自动兼容」；没有它，每次升级都要人工判断。

所以定位是：**版本 = 语义接口，哈希 = 完整性锚点**，两者都进锁（§5.5）。

### 5.2 解析算法：推荐 MVS（最小版本选择）

#### 5.2.1 算法定义（一段话 + 一张表）

设每个包 `m` 的每条依赖要求是一个**下界**（`>= v` 或精确 `= v`）。MVS 的答案：

> 对每个包 `m`，选中版本 `S(m) = max{ v | (m, >=v) 或 (m, =v) 出现在闭包里 }`；
> 从根清单出发求闭包，迭代到不动点（新增的包可能带来新的下界）。

性质：**单调**（加一条要求只会让版本变大或不变）、**唯一**（不动点唯一，与遍历顺序无关）、**O(边数)**、**无回溯**、**结果只依赖清单**（注册表后来发新版本不影响已有锁）。这五条正是「可预测」的技术含义。

清单里的 `^1.4.2` 在解析时**只贡献下界** `>=1.4.2`；它的「上界」不需要写进算法，因为上界就是**兼容边界**（major，或 0.x 的 minor），而边界已经进了身份（§5.3）——超出边界的版本对同一逻辑名来说是「另一个包」，会在 R-2 处被拦下。这也是为什么清单**不提供** `~`/`<`/`<=`：一旦允许写 minor 级上界，就得引入真正的范围求解，MVS 的可预测性随即消失。

| 场景 | MVS 的结果 | 说明 |
|---|---|---|
| A 要 `C>=1.0`，B 要 `C>=1.2` | `C 1.2` | 取最大下界 |
| A 要 `C>=1.0`，B 要 `C>=1.2`，C 最新是 1.9 | `C 1.2`（**不是 1.9**） | 反直觉但关键：MVS 只满足「下界」，不追新。**新增依赖时把当时最新版写成下界**（Go 的 `go get` 语义），`update` 才提升 |
| A 要 `C=1.2`，B 要 `C>=1.5` | **错误** | 精确 pin 与下界矛盾；报错指出两条要求（§5.10） |
| A 要 `C>=1.0`，B 要 `C>=2.0` | **不是 MVS 失败**，是**身份问题**：1.x 与 2.x 不兼容 → 见 §5.3（默认报错 + 给三种出路） | major 分叉不走求解器 |
| 多个包互相依赖成环 | **错误** | 编译期已有循环导入检测（`driver_build.cpp:373-381`），解析期也要先报 |

#### 5.2.2 为什么不是 SAT / 回溯（PubGrub、pip、Cargo 那一类）

| 维度 | MVS | 回溯 / SAT（PubGrub 类） |
|---|---|---|
| 最坏复杂度 | O(边数)，一遍闭包 | 最坏指数；实践中有「解析很久/太深」的著名案例（pip 文档与社区） |
| 结果确定性 | 只依赖清单集合 → **完全确定** | 依赖「当时可见的版本集合」；同一份清单下周可能解出不同结果 → 必须靠锁兜底 |
| 可解释性 | 「选了 1.2，因为它是所有下界里最大的，来自 B」——一句话 | 需要冲突驱动学习式的解释链；错误消息能写得很长但仍难读 |
| 能否表达上界 | 不需要（见下） | 能，但正是上界制造了大多数冲突 |
| 新版本发布的影响 | 零（除非 `update`） | 可能悄悄改变结果 |
| 实现复杂度 | 低 | 高 |
| 何时需要它 | 需要「在多个可行解里挑最优」 | 需要范围代数 + 上界 + 依赖不兼容的组合约束 |

**关键论点：在我们这个模型里，「major 上界」这个需求可以被身份设计消灭。** 「我不想用 2.x」在别的生态靠 `>=1, <2` 表达；在我们这里，**2.x 本来就是另一个兼容边界之外的版本**（边界进标识，§5.3），根本不会和 1.x 抢同一个名字。代价是 minor 级上界（`~`）不能表达——我们选择不支持它，而不是假装支持（见 5.1.3）。于是：

- 用不到范围代数 → 用不到求解器；
- 剩下的唯一「求解」是求最大下界 = MVS。

这不是「MVS 更简单所以选它」，而是**先用身份设计把问题变简单，再选算法**。如果哪天我们不得不引入 feature/条件编译这类「同版本不同配置」的维度（§7-Q3），上界与组合约束会回来，那时再评估 PubGrub——而不是现在就背它的复杂度。

#### 5.2.3 MVS 的两个已知弱点与对策

| 弱点 | 表现 | 对策 |
|---|---|---|
| 「下界声明不准」 | 库作者写 `>=1.0` 但其实需要 1.2 的 API → 用户拿到 1.0 就编不过（Go 社区的经典抱怨） | (a) 新增依赖时写**当时最新**的下界（工具默认，不是人肉）；(b) `update --check-lower-bounds` 定期用最低版本跑一遍构建；(c) 编译错误会直接暴露缺 API，比运行期错好 |
| 「不追新」 | 用户以为 `build` 会拿最新 | `update` 显式提升；`deps explain` 显示「为什么是这个版本」；`--prefer-newest` 只影响 `update` 的候选顺序 |

#### 5.2.4 解析的产物

解析（`resolve` / `update`）输出**锁文件**（§5.5），其中对每个包记录：坐标、版本、源码哈希、来源、以及**入边（谁要求的、要求什么）**。入边是「可解释性」的燃料，也是 `deps why` 的数据源。

### 5.3 多版本共存 vs 单一版本：明确立场

#### 5.3.1 三种可选立场

| 维度 | ① 硬单版本（Go / NuGet CPM / vcpkg） | ② 自动按 major 多版本（Cargo / Deno URL） | ③ 默认单版本 + 显式别名（**本文推荐**） |
|---|---|---|---|
| 钻石（major 分叉） | 无解：报错或逼升级 | 自动并存，程序能编过 | 报错 + 给「加别名」出路；人决定 |
| 类型身份 | 永远清晰（一个名义一个类型） | **分裂**：同名两类型，不能互传，用户困惑 | 分裂，但**用户显式选择了它**，诊断能指回别名 |
| 用户心智 | 简单 | 「为什么有两个版本？」 | 简单（默认单版本），例外有名字 |
| 实现成本 | 低 | 中（符号/类型都要版本化） | 中（同②，只是默认不触发） |
| 缓存友好 | 中（产物键不带版本） | 好（版本进键） | 好（版本**总是**进键，见 5.3.4） |
| 生态压力 | 大（逼库作者不许破坏） | 中 | 小（渐进升级/插件场景有逃生阀） |

#### 5.3.2 立场

> **默认单版本**：同一个逻辑 import 名在同一张图里只对应一个版本。
> **显式别名才允许并存**：只有人在清单里声明别名时，才允许跨兼容边界并存；编译器保证两者符号不同、类型不同、不隐式转换。
> **绝不静默多版本。**

#### 5.3.3 为什么（三条理由，各自对应一种失败模式）

1. **静默共存会把解析问题变成类型系统问题。** Cargo 允许 `rand 0.7` 与 `rand 0.8` 并存，代价是 `rand::Rng` 是两个类型、不能互传；用户看到的不是「版本冲突」，而是「trait 不匹配」——错误离根因更远。我们的类型系统是 nominal 的（`ImportedClass` 带 `origin_module`，`module.h:19-25`），一旦并存，`pkg_json@1` 的 `Decoder` 与 `pkg_json@2` 的 `Decoder` 是两个类型，报错会出现在**每一个跨版本边界**，而不是在解析阶段一次说清。
2. **硬单版本会逼出更糟的隐式多版本。** 如果 major 分叉只能靠「升级所有依赖」解决，团队会去 fork、去 vendor、去复制粘贴——那是**没有名字、没有锁、没有审计**的多版本，比显式别名糟得多。给一个受控逃生阀，比堵死更安全。
3. **编译型 + 静态符号让并存技术上很便宜**（见 5.3.4）。既然成本低、而禁止它会把成本转嫁给用户，就用「显式开关」而不是「一刀切」。

#### 5.3.4 技术上为什么可行（编译型语言的礼物，也是必须做对的地方）

| 层面 | 现状 | 并存需要什么 | 难度 |
|---|---|---|---|
| 符号 | `pyadamas$<module>$g$<name>`（`module.cpp:466`）；模块名 = 符号前缀 | **版本进 mangling** → 两个版本符号天然不同 | 低（改字符串生成 + 接口格式） |
| 接口 | 每个模块一份 `.pya`，含 `origin_module`/`qualname` | 接口里记**包坐标**，`origin` 升级成 `(registry, ns, name, version, module)` | 低 |
| 类型身份 | `ImportedClass.cls` 是独立 `ClassInfo`，带 `origin_module` | 身份定义加版本维度；跨版本 = 不同类型（自动成立） | 低（诊断要补） |
| 链接 | 全部 `mod.o` 静态链接（`driver_build.cpp:981-1019`） | 两套符号 = 两份代码，链接器不冲突 | 零（只要符号不同） |
| 运行期 | 类对象/vtable 都是静态的，`ctor_symbol` 在接口里 | 两个版本各有自己的 `pyadamas$<mangled>$n$Cls` | 零 |
| 缓存 | 键含模块名+路径 | 键含**包坐标+版本**（本来就该含） | 低 |
| 诊断 | 现有「传入类型不匹配」 | 要额外指出「这是 `pkg@1` 的 T，需要的是 `pkg@2` 的 T」 | 中（消息质量工作） |

**关键结论：并存的技术成本几乎全在「命名与身份」，不在运行时。** 所以正确的做法是**从一开始就把版本编进标识**（P0 就定），而不是等到 P4 再改——否则缓存键、接口格式、符号规范全要重做一轮。

#### 5.3.5 规则细节

| # | 规则 | 失败时的行为 |
|---|---|---|
| R-1 | 同一逻辑名、所有要求都落在**同一兼容边界**（major，或 0.x 的 `0.minor`）且存在最大下界 → MVS 选一个版本 | 正常 |
| R-2 | 同一逻辑名、出现**跨兼容边界**的要求 → 默认**报错**，附两条要求链与三种出路（升级/降级 override、加别名、拆程序） | 解析失败（可解释） |
| R-3 | 清单里声明别名 `json2 = { package = "pkg-json", version = "2" }` → 逻辑名 `json2` 绑定到 `pkg-json@2.*`；源码写 `import json2` | 正常，两个版本并存 |
| R-4 | 别名之间**不共享类型**：`pkg@1` 的类传给 `pkg@2` 的形参 = 编译错误 | 类型错误 + 指出两个坐标 |
| R-5 | 禁止隐式转换/自动适配（不做序列化、不做「同名字段拷贝」） | 编译错误 |
| R-6 | 同一兼容边界内**禁止**并存两个版本（必须合并） | 解析器直接取 max |
| R-7 | stdlib 内置模块（native）**不可**被别名/包占用 | 解析错误（保留名） |
| R-8 | 别名数量不设上限，但 `deps tree` 会把它们标出来（让成本可见） | — |

为什么 R-6 重要：同 major 内两个版本并存**没有任何好处**（它们兼容、类型应该统一），只会制造两份代码、两份类型、双倍编译。Cargo 也只在 major 分叉时并存，同一道理。

#### 5.3.6 代价（诚实记录）

| 代价 | 量级 | 何时付 |
|---|---|---|
| 接口格式与 ABI 版本升级（`kModuleFormatVersion`/`kModuleAbiVersion`，`module.h:54-55`） | 一次性：所有缓存失效一次 | P0 定命名时一起定 |
| 符号变长（`pyadamas$pkg_json_1_4_0$g$dumps`） | 汇编体积与可读性；本来就有 `pyadamas$` 前缀与 `$` 分隔符（`codegen_emit.h:239` 注释提到 mangled 名含 `$`） | 一次性 |
| 缓存键必须带版本 → 不同图的产物不通用 | 无害（本来就该不同） | 一次性 |
| 用户偶尔会问「为什么有两个版本」 | 靠 R-2 的错误消息与 `deps tree` 解释 | 每次并存时 |

### 5.4 缓存与存储（「包共用缓存」的正解）

#### 5.4.1 三层 store

| 层 | 内容 | 键 | 谁共享 | 大小量级 |
|---|---|---|---|---|
| S1 源码 store | 解包后的源码树（只读） | 源码树哈希（SHA-256，对排序后的相对路径 + 内容） | **全局**（跨项目、跨机器） | KB–MB |
| S2 接口 store | `.pya` 接口文件 | 模块编译键（见 5.4.3） | 全局 | KB |
| S3 产物 store | `mod.o`（可选 `mod.s`）+ 清单 | 模块编译键 | 全局（受编译器/目标/开关约束） | KB–MB/模块 |

**为什么要分两级（源码 + 产物）而不是像 pnpm 那样只有一层**：pnpm 的包是「已发布的最终形态」，取来即用；我们的源码取来还要编译，而**编译结果比源码大一个量级且键更复杂**。两者共享范围相同但失效规则不同：源码只按内容失效，产物还要按编译器/开关/依赖接口失效。混成一层会让「源码命中但产物不命中」的情况无法表达。

#### 5.4.2 布局草案

```
$PYADAMAS_HOME/                          # 默认 ~/.local/share/pyadamas（可用环境变量覆盖）
  store/v1/
    src/sha256/<前2位>/<hex>/            # S1：源码树，只读（0444/0555）
    iface/<key-hex>/mod.pya              # S2
    obj/<key-hex>/{mod.o,manifest}       # S3（debug 模式下可选 mod.s）
    tmp/<pid>-<rand>/                    # 原子写中转（写完 rename）
    gc.lock  leases/<key-hex>.<pid>      # GC 租约
  registry-cache/                        # 元数据缓存（解析用，可过期）
  config.toml                            # 默认注册表、镜像顺序、store 路径
```

项目侧**只有**：

| 文件 | 作用 | 进 git？ |
|---|---|---|
| `pyadamas.toml` | 清单：直接依赖、别名、目标、开关 | 是（人写） |
| `pyadamas.lock` | 锁：完整图 + 坐标 + 哈希 + 入边 | 是（机器写，人审） |
| `.pyadamas/` | 本次构建的派生状态（模块解析表、上次构建指纹） | 否（可随时删，纯派生） |

**没有** `node_modules` / `vendor` 式物化目录（除非显式 `vendor`）。这就是「避免 node_modules 式的上帝包管理灾难」在结构上的答案：**项目里不存在一棵依赖树**，只有一张表和一堆内容地址。

#### 5.4.3 编译键（本设计最容易出错的地方）

现状已经有 15+ 个开关进清单，并且代码里留了一条血泪注释（`driver_build.cpp:175-180`）：

> 「环境变量会改变代码生成结果，但缓存键只有『模块名 + 源文件路径』，不含任何编译选项。不把它写进清单就会出现『切了开关仍命中旧产物』——实测导致连续几轮 A/B 测试拿到完全相同的二进制，性能结论全错。」

这条教训直接推出设计原则 D-3：**键必须穷举所有影响产物的输入**。逐项对照：

| 键成分 | 现状 | 是否充分 | 目标 |
|---|---|---|---|
| 模块源码内容 | `fnv1a64(source)` 进清单（`driver_build.cpp:345`） | 用于失效可以；**不能当信任锚** | SHA-256（与锁一致）；FNV 可留作快速预检 |
| 模块身份 | 缓存目录 key = `sanitize_symbol(name)` + `fnv1a64(path)`（`driver_build.cpp:147`） | **不充分**：移动项目即 miss；sanitize 有损（`driver_modules.cpp:15-21`） | 包坐标 + 单射 mangled 名（§5.6） |
| 包版本 | 无 | 不充分（多版本场景下无法区分） | 进键（P0 就定） |
| 编译器身份 | `/proc/self/exe` 的 size+mtime + `rt.o` 的 size+mtime（`driver_build.cpp:132-144`） | **不充分**：不可跨机；mtime 在拷贝/恢复后不可信 | 编译器内容 SHA-256 + 版本串 + 目标 |
| 目标 ABI | **不在清单**（`driver_build.cpp:166-208` 的字段表里没有） | **现存缺口**：`--target=win64` 改变调用约定/影子空间，却会命中另一 ABI 的 `mod.o` | 进键（P3 必做，并补一条回归） |
| 代码生成开关（opt/fastmath/zerocostexc/rcsplit/raopt/simd/vect/avx2/loopopt/inlineopt/borrowopt/typetags/dynamicbig/langgaps/csymdefault） | 全在清单 | 充分（这是做得对的地方） | 保持；新增开关**必须**同步加字段 + 加「漏掉会误命中」的测试 |
| 依赖接口哈希 | `dep <name> <interface_hash>`（`driver_build.cpp:363-369`、`601-608`） | 在「无跨模块代码生成」前提下充分（early cutoff） | 保持；若开跨模块内联/LTO **必须**改成依赖实现哈希（§7-Q4） |
| 依赖实现哈希 | 无 | 将来不充分 | 仅在开启跨模块优化时加入 |
| 运行期 `rt.o` | 通过 `toolchain_id` 的 mtime 间接覆盖 | 不充分（不可移植） | 内容哈希 |
| 汇编器/链接器 | 无 | 语义上无影响（只影响 .o 字节） | 可选：进「可复现验证」而不是失效键 |
| 路径无关性 | 清单无路径，但 `interface_hash` **含绝对 source_path**（`module.cpp:498`、`666`） | **破坏跨机一致** | 接口里去掉绝对路径（只留坐标/相对路径）→ P0/P1 |

#### 5.4.4 失效传播

| 变化 | 重编范围 | 机制 |
|---|---|---|
| 模块源码，**接口不变** | 只该模块 | `interface_hash` 未变 → 下游不重编（early cutoff；前提是没有跨模块内联） |
| 模块源码，**接口变** | 该模块 + 传递下游 | 清单里的 `dep` 哈希比对（现状就是这样） |
| 包版本变化 | 该包全部模块 + 下游 | 版本进 mangling → 下游符号也变 |
| 任一代码生成开关 | **全图** | 开关进键（现状已覆盖大部分，缺 target） |
| 编译器/运行时变化 | 全图 | 编译器内容哈希进键 |
| 锁变化但解析结果相同（只改了注释/顺序） | **不重编** | 键是内容，不是锁文件字节 |
| 开启跨模块内联（未来） | 下游按实现哈希 | 需要新增键成分 |

#### 5.4.5 GC 策略

| 项 | 设计 | 理由 |
|---|---|---|
| roots | 所有**已登记项目**的锁文件（登记表由 `pyadamas` 在 fetch/build 时维护）+ 显式 `--gc-roots` | 与 pnpm `store prune` 同构：可达性，不是 LRU |
| 标记 | 从锁里的树哈希/编译键出发 | 键是内容地址，天然可标记 |
| 清除 | 未标记 **且** mtime 早于宽限期（默认 30 天） | 防止删掉「刚 fetch 还没构建」的条目 |
| 并发 | 构建对用到的 key 建 **lease**（`leases/<key>.<pid>`，含开始时间）；GC 跳过未过期 lease | 避免删掉正在使用的产物 |
| 原子性 | 只写 `tmp/` 再 rename（现状已有 `cache_temp_path` / `write_atomic`，`driver_build.cpp:79-87`） | 并发写不会读到截断文件（`tests/cache_race.sh` 的教训） |
| 读校验 | 读 .o/.pya 时校验尺寸 + 哈希；失败 = 报错并删除该项 | **缓存不可信**（uv 的 cache safety 一节持同样立场）：共享 store 可能被污染/半写 |
| 危险动作 | `gc --prune` 默认 dry-run；`--yes` 才真删 | 不可逆操作必须显式 |

#### 5.4.6 共享 vs 隔离

| 模式 | 适用 | 做法 |
|---|---|---|
| 默认 per-user store | 单机开发 | `~/.local/share/pyadamas/store`；权限 0700 |
| 共享 store（可选） | CI/多用户机器 | 路径由 `PYADAMAS_HOME` 指向；条目只读、写入走原子 rename；GC 由单一管理员/定时任务跑 |
| 私有 store | 不可信输入/审计环境 | `--store <dir>` 每项目一份；不共享但可复现 |

**为什么共享 store 必须「读时校验」**：共享带来两个新失败模式——(a) 别的进程/用户写坏了一个条目；(b) GC 与构建竞态。校验 + lease 是这两个问题的正面答案，而不是「相信缓存」。

### 5.5 锁文件

#### 5.5.1 定位与格式

```
lock 1                                        # 格式版本（必填第一行）
toolchain pyadamas 0.447 target x86_64-sysv   # 仅记录信息，不参与解析

pkg json   pkg-json@1.4.0    sha256:<tree>  modules=json=src/json.py  from=default
pkg json2  pkg-json@2.1.0    sha256:<tree>  modules=json=src/json.py  alias=json
pkg http   @acme/http@2.0.1  sha256:<tree>  modules=http=src/http/__init__.py,http.client=src/http/client.py

dep json   http    ">=2.0.1"        # 谁依赖谁、要求什么（可解释性的燃料）
dep json2  http    ">=2.0.1"
dep http   (root)  ">=2.0.1"        # 直接依赖
```

（格式草案；字段在 P0 定稿。要点：**行式、可排序、可 diff、无嵌套**。）

#### 5.5.2 必须满足的性质

| 性质 | 具体要求 | 反例（历史） |
|---|---|---|
| 确定性 | 同一输入的两次解析 **字节相同**：键排序、无时间戳、无主机名、无绝对路径、LF、UTF-8 NFC | npm 锁在不同版本工具下格式漂移 |
| 完整性 | 每个包都有**内容哈希**（树哈希）；哈希是解析结果的一部分 | 无哈希的 requirements.txt 是假锁 |
| 全图 | 含**传递依赖**，不只直接依赖 | 只锁直接依赖 = 下次装出来不一样 |
| 可重建图 | 有 `dep` 边（谁依赖谁、要求什么） | 扁平列表无法回答「为什么装了它」 |
| 可表达多版本 | 逻辑名（别名）与包坐标**分离** | 只有「名字→版本」一列，无法表达两份 |
| 可校验 | `--locked` 能判断「当前清单是否会产出不同锁」并给 diff | install 静默改锁 |
| 可审计 | 有来源（registry/URL）与哈希，能进 SBOM | 「从某处装的」不可追溯 |
| 与工具链解耦 | 记录编译器信息但**不参与解析**；解析结果与编译器版本无关 | 锁里写死本机路径 → 换机器即失效 |

#### 5.5.3 与清单的分工

| 问题 | 清单（人写） | 锁（机器写） |
|---|---|---|
| 我要 ^1.4 的 json | 是 | — |
| 最终是 1.4.2 | — | 是 |
| 它的源码哈希 | — | 是 |
| 谁依赖了它、要求什么 | 部分（直接依赖） | 是（全图） |
| 我的别名 json2 指向谁 | 是 | 是（固化） |
| 编译器/目标 | 是（项目配置） | 仅记录 |

**默认构建只读锁**。清单与锁不一致（比如手改了清单没跑 `update`）→ **报错**并打印「清单要求 X，锁记录 Y，运行 `pyadamas update`」，而不是悄悄重解析。这是「不做清单/锁漂移」的强制点（§4.6）。

**为什么只要一个锁文件**：Go 需要 `go.mod` + `go.sum` 两份（意图/校验），NuGet 需要 manifest + assets + 可选 `packages.lock.json`。两份文件就多一个「谁对」的问题。我们的清单已经承担「意图」，锁同时承担「精度 + 完整性」，两者职责不重叠。代价是锁文件略大（每包多一行哈希），可接受。

### 5.6 与编译器的集成

#### 5.6.1 引入「模块解析表」（ModuleMap）作为编译输入

现状：编译器自己按路径搜（`driver_modules.cpp:37-79`）。目标：**包模块只能通过解析表进入构建**。

```
# 由 lock 派生（.pyadamas/modules.map，机器生成，删了可重建）
module json        -> mangled=pkg_json_1_4_0$json   src=store/src/sha256/…/json.py   pkg=pkg-json@1.4.0
module http.client -> mangled=acme_http_2_0_1$http$client …
```

| 好处 | 说明 |
|---|---|
| 幽灵依赖不可能 | 不在表里的包模块 = 未声明 = 编译错误（§4.9）；编译器本来就会扫 import（`driver_modules.cpp:256-352`），强制成本近似为零 |
| 确定 | 同一张表 → 同一解析结果，与目录内容、`-I` 顺序无关 |
| 可缓存 | 表是纯数据，键是内容地址；不需要「先搜路径再猜缓存键」 |
| 可解释 | 「为什么解析到它」有现成答案（表里的来源 + 锁里的入边） |

#### 5.6.2 解析优先级（有清单时）

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | 相对导入（`from . import x`） | 现状语义，不变（`driver_modules.cpp:272-296`） |
| 2 | 本包内绝对模块 | 包内可见性规则（§7-Q2） |
| 3 | 项目本地模块（入口目录） | 现状语义，保持；但与包**同名**时报错（见 5.9） |
| 4 | ModuleMap（清单依赖） | **唯一**包入口 |
| 5 | stdlib Python 源 | 现状：用户文件可覆盖（`driver_modules.cpp:191-207` 的「用户可覆盖」语义）——有清单时建议收紧 |
| 6 | 内置 native | **不可覆盖**（现状已如此） |

#### 5.6.3 符号命名（mangling）

要求三条：**单射**（不同坐标 → 不同符号）、**稳定**（坐标不变 → 符号不变）、**可读**（诊断里能反推）。

| 项 | 现状 | 目标 |
|---|---|---|
| 前缀 | `pyadamas$` | 保留（`codegen_emit.h:239` 已依赖 `$` 合法） |
| 模块部分 | `sanitize_symbol(module)`：非字母数字→下划线（**有损**） | 单射转义：`-`→`_2d_`、`.`→`_2e_`、`@`→`_40_`…；或统一用「包坐标哈希前 12 位」+ 可读后缀 |
| 版本 | 不出现 | `pkg_json_1_4_0`（major/minor/patch 都在，保证不同版本不同符号） |
| 本地/入口模块 | `pyadamas$<mod>$…`（现状） | 保持现状（图局部，不需要跨图复用） |
| 长度 | 短 | 加版本后变长；现有代码已证明 `$` 符号在汇编/目标文件里合法，但超长符号名的工具容忍度**待核实**（建议设 200 字符上限并做单测） |

为什么单射必须现在就做：现在模块名被限制为标识符（`valid_module_name`，`driver_modules.cpp:23-28`），所以有损 sanitize 不会碰撞；一旦包名允许 `-`，`pkg-json` 与 `pkg_json` 会撞成同一个符号——这是**静默错链接**，比编译错误糟得多。

#### 5.6.4 接口文件（.pya）变更清单

| 变更 | 现状 | 原因 |
|---|---|---|
| 去掉绝对 source_path | 编码在头部（`module.cpp:498`），且进 `interface_hash`（`666`） | 可复现（§4.10）；换目录/换机器接口哈希不该变 |
| 增加包坐标 | 只有 `name` / `origin_module`（`module.h:27-46`） | 类型身份与多版本（§5.3） |
| 增加 mangle 名 | 只有逻辑名 | 跨包链接要用物理名 |
| 保留 origin_qualname 的用户可见性 | 用 `runtime_name + "." + name`（`driver_build.cpp:794-797`） | **版本不进用户可见的 __qualname__**：身份是编译期的，展示名是逻辑的 |
| 升级 kModuleFormatVersion / kModuleAbiVersion | 12/1（`module.h:54-55`） | 上述字段变化 → 必须 bump，旧缓存一次性失效 |
| 哈希算法 | `interface_hash` 用 FNV-1a 64（`module.cpp:666`） | 本地失效可以用 FNV；**锁/信任用 SHA-256** |

#### 5.6.5 缓存目录与增量编译

| 项 | 现状 | 目标 |
|---|---|---|
| 缓存目录 | `<build>/modcache/<name>-<pathhash>`（`driver_build.cpp:146-153`） | `$STORE/obj/<compile-key-hex>`（内容寻址、跨项目） |
| 命中判定 | 清单逐字段比对（`try_cache`，`driver_build.cpp:581-625`） | 直接按 key 查存在性 + 读 manifest 自检 |
| 包级聚合 | 无 | 可选：每个包一份「模块 key 列表」，减少 N 次 stat/读 |
| 并行 | 逐模块串行（`driver_build.cpp:962-978`） | 独立优化项：store 并发安全是前置（已由 lease + 原子写保证） |
| check 模式 | 只读接口、不编译依赖（`load_check_lookup`，`driver_build.h:106-109`） | 保持，且可直接命中 S2 → check 完全不需要依赖产物 |

#### 5.6.6 全程序链接与「不发二进制」

链接仍然是「全部 `mod.o` + `rt.o`」（`driver_build.cpp:981-1019`）。由此：

| 结论 | 理由 |
|---|---|
| **不做二进制分发**（P5 之前） | 没有跨包 ABI 面，发布二进制必须绑定编译器版本/目标/全部开关，组合爆炸；源码分发 + 本地编译是可复现的默认 |
| 跨机共享**缓存**是安全的 | 键相同 → 产物内容相同（在编译器/目标/rt 完全一致时）；这与「发布不可信二进制」是两件事 |
| 不生成 .a/.so | 没有外部消费者；包 = 一组模块，不是链接单元 |
| 全程序优化（LTO）需要改键 | 见 §7-Q4；在键里加依赖实现哈希，或把可内联体放进接口（类似 C 的 static inline） |

### 5.7 离线与审计

#### 5.7.1 三阶段流水线（联网/离线边界清晰）

| 阶段 | 联网 | 输入 | 输出 | 可重复性 |
|---|---|---|---|---|
| fetch | **是**（唯一联网阶段） | 锁里的坐标/哈希 | store 里的源码树 | 幂等；哈希不符即失败 |
| resolve / update | 是（读注册表元数据） | 清单 + 注册表元数据 | 新锁 | 幂等（同输入同字节） |
| build | **否**（默认拒绝联网） | 锁 + store + 编译器 | 二进制 | 确定性目标（§5.7.4） |

#### 5.7.2 镜像与多源

| 机制 | 设计 | 类比 |
|---|---|---|
| 源列表 | 有序列表，逐源尝试；失败继续下一个；最终失败才报错 | Go `GOPROXY`（逗号分隔 + direct/off） |
| file:// 镜像 | 一个符合 store 布局的目录即可当源（拷贝/同步即镜像） | 内网离线最常见 |
| 元数据缓存 | 注册表响应带 ETag/过期时间；`--offline` 只用缓存 | pip/uv 的 HTTP 缓存 |
| 完整性 | 每个源返回的内容都要匹配锁里的哈希；**换源不降低校验** | — |

#### 5.7.3 vendor 模式（内网/审计的逃生阀）

| 项 | 设计 |
|---|---|
| 目录 | `vendor/<sha256>/…`（内容寻址，不是人类目录树）+ `vendor.lock`（本次 vendor 覆盖的坐标与哈希） |
| 构建 | 有 `vendor/` 时优先从 vendor 读，等价于本地源 |
| 校验 | `--check-vendor`：vendor 与锁不一致 → **报错**（Go 的 `vendor/modules.txt` 一致性检查的教训） |
| 体积 | vendor 是源码（MB 级），提交与否由团队决定；**默认不进 git**，CI 用 fetch 预热 store |

#### 5.7.4 审计与可复现

| 能力 | 设计 |
|---|---|
| SBOM | `pyadamas sbom --format spdx` 或 `cyclonedx`：从锁生成坐标 + 版本 + 哈希 + license（license 需注册表元数据） |
| 构建清单 | 每个模块的编译键 + 编译器身份 + 目标，落盘为 `build-manifest.json`（供审计/重建） |
| 可复现检查 | `--reproducible`：禁用绝对路径、时间戳、随机顺序；校验接口里无本机路径 |
| 重建验证 | `rebuild-verify`：用锁从 store 重编，比对产物哈希；这是「构建可信」的最终证据 |
| 审计问题 | `deps why <module>` / `deps tree` / `sbom` 三者覆盖「谁引入、引入什么、内容是什么」 |

### 5.8 信任模型

#### 5.8.1 威胁 → 机制

| 威胁 | 机制 | 我们的对策 | 阶段 |
|---|---|---|---|
| 注册表/镜像篡改内容 | 内容哈希 | 锁里的树哈希是信任根；下载后校验；store 读时校验 | P1 |
| 版本被重写（1.4.0 换了内容） | 不可变发布 | 坐标+哈希绑定；校验失败即拒绝；撤回用 retract（不删历史） | P1 |
| 名字劫持 / 依赖混淆 | 作用域 + 保留名 | 内部包必须 scoped；stdlib 名保留；锁记完整坐标（registry + namespace） | P2 |
| 发布者账号被盗 | 签名 | **P4 可选**：registry 提供发布者签名/透明日志；锁里记录签名引用 | P5 |
| 依赖树里有恶意包 | 审计 + 最小权限 | 无 install 脚本（§4.5）→ 攻击面只剩「源码被编进二进制」；SBOM 让审计可行 | 持续 |
| 缓存被污染 | 读校验 | 见 5.4.6 | P3 |
| 供应链透明度 | 透明日志 | 可选：(name, version, hash, 时间) 追加日志 | P5 |

#### 5.8.2 签名：做，但不要现在做

| 问题 | 结论 |
|---|---|
| 哈希够不够 | **够用于完整性**（内容没变），不够用于**来源认证**（谁发布） |
| 现在要不要做 | 不要。没有注册表和发布流程时，签名只是空转；先把「内容不可变 + 哈希进锁 + 读校验」做扎实 |
| 将来怎么做 | 与注册表一起做：发布者身份（namespace 所有权）+ 对「坐标+哈希」的签名；客户端可选验证；透明日志记录追加历史 |
| 明确不做 | 运行期签名校验（没有运行期）；TOFU 式「第一次见就信任」的静默信任；把签名当哈希的替代品 |

### 5.9 与现有「本地 import」的兼容

#### 5.9.1 兼容策略：两条路并存，默认走老路

| 项目形态 | 解析方式 | 保证 |
|---|---|---|
| 没有 `pyadamas.toml` | **完全现状**：路径搜索（`driver_modules.cpp:37-79`）、`-I`、stdlib 兜底 | 现有用例 0 回归（D-7） |
| 有清单 | 本地模块仍走路径搜索；**包模块只走 ModuleMap** | 新机制不侵入老机制 |

#### 5.9.2 冲突规则

| 情形 | 行为 | 理由 |
|---|---|---|
| 同一逻辑名解析到两个文件 | **错误**（现状已是：`module 'x' resolves to two different files`，`driver_build.cpp:487-494`） | 单值名字空间是正确性前提 |
| 本地模块与包提供同名模块 | **错误**，消息给出两个来源与解法（改名/别名/换布局） | 静默覆盖会让人永远搞不清用的是哪个 |
| 两个包提供同名模块 | **错误**（除非别名） | 同上 |
| 包占用 stdlib 名 | **错误**（保留名） | 语言语义不能因装包而变 |
| `-I` 指向的目录里有包模块 | 只有 legacy 模式会看到；清单模式忽略并**警告** | `-I` 是逃生口，不是机制（§4.8） |

#### 5.9.3 -I 的命运

| 阶段 | -I 角色 |
|---|---|
| P0 | 仍然可用（本地模块/legacy） |
| P2 | 清单项目里对包模块**无效**（只影响本地模块） |
| P5 | 文档标记为 legacy；新项目模板不生成 |

### 5.10 失败模式与可解释性

#### 5.10.1 三条诊断命令

| 命令 | 回答 | 数据源 |
|---|---|---|
| `deps tree` | 图长什么样（谁依赖谁、几个版本） | 锁的 dep 边 |
| `deps why <module>` | 为什么这个模块在我的构建里（哪条链引入的） | 反向边 + 别名 |
| `deps explain <pkg>` | 为什么选这个版本（max-of-minimums 的见证） | 入边要求集合 |

#### 5.10.2 错误消息模板（人话优先）

```

  required by app (pyadamas.toml:12):        json ^2.0
  required by @acme/http (2.0.1, http):      json ^1.4
  these are incompatible majors (1.x vs 2.x); a single import name can bind one version.
  3 ways out:
    1. upgrade @acme/http to a version that accepts json 2.x   (pyadamas update http)
    2. keep both, with explicit aliases:  json2 = { package = "pkg-json", version = "2" }
       then import json2 wherever you need 2.x (types will NOT be interchangeable)
    3. split the program so the two requirements live in different binaries
```

```
error: source hash mismatch for pkg-json@1.4.0
  lock:   sha256:9f2c…
  source: https://mirror.corp.example/pkg-json/1.4.0.tar.zst
  got:    sha256:1a77…
  the registry content changed or the mirror is corrupt; refusing to use it.
```

```

  expected: json.Decoder  = pkg-json@2.1.0:json.Decoder
  got:      json2.Decoder = pkg-json@1.4.0:json.Decoder
```

#### 5.10.3 可解释性的三条硬约束

| 约束 | 含义 |
|---|---|
| 纯函数 | 同样（清单、锁、注册表快照）→ 同样结果与同样错误；不受环境变量/时钟/网络顺序影响 |
| 见证齐全 | 每条冲突消息必须给出**所有**相关要求与来源（文件:行 或 包坐标） |
| 双向可查 | 既能「向上问为什么选它」（why），也能「向下问它带进来什么」（tree） |

### 5.11 关键决策汇总（一页看完）

| 决策点 | 选择 | 一句话理由 | 被否的替代 |
|---|---|---|---|
| 解析算法 | **MVS** | 可预测、可解释、O(边数)；上界需求被身份设计消灭 | SAT/回溯：结果依赖注册表状态、解释成本高 |
| 多版本 | **默认单版本 + 显式别名并存** | 静默共存会把解析问题变成类型问题；硬禁止会逼出隐式 fork | 自动按 major 并存（Cargo 式）、硬单版本（Go 式） |
| 缓存 | **全局内容寻址 store（源码+产物两级）+ 项目侧只存表** | 这才是「共用缓存」；项目里没有依赖树 | per-project 缓存、嵌套树、vendor 为默认 |
| 锁 | **单文件、含全图+哈希+入边、默认 --locked** | 消灭漂移；一份文件一个真相 | 清单+锁两份、无哈希的假锁 |
| 构建集成 | **ModuleMap 作为编译输入** | 幽灵依赖不可能；解析确定、可缓存 | 继续路径搜索 + -I |
| 符号 | **版本进 mangling、单射编码** | 并存的前提；避免静默错链接 | 保持现状（无法多版本）、有损 sanitize（会撞名） |
| 分发形态 | **只发源码**（二进制仅作缓存） | 没有跨包 ABI，只有缓存键一致时才可复用产物 | 预编译包（ABI 组合爆炸） |
| 脚本 | **不做任何构建期脚本** | 模型推论：没有安装步骤 | install/postinstall/build.rs |
| 信任 | **哈希为根、签名后置** | 先做不可变与校验，再谈身份 | 先签名后哈希（本末倒置） |

## 6. 分阶段落地路线

排序原则：**先让「输入」确定（锁），再让「输入」可共享（store），再让「解析」自动化（registry），再让「产物」可共享（缓存），最后才碰最贵、最容易翻车的「多版本」。**

每个阶段都给六项：**目标 / 交付 / 验收 / 不做会怎样 / 解锁什么 / 主要风险**。验收标准尽量写成可执行命令或可观察现象，不写「感觉对了」。

### 6.1 P0 · 锁文件 + 路径依赖（无注册表）

| 项 | 内容 |
|---|---|
| 目标 | 把「一次构建的输入」变成可复现、可审阅的产物 |
| 交付 | (a) `pyadamas.toml` 最小清单（path 依赖 + 别名 + 模块映射）；(b) `pyadamas.lock`（§5.5 格式）；(c) `resolve` / `--locked`；(d) 编译器接受 ModuleMap 文件（新输入，legacy 模式默认不变）；(e) 版本进 mangling 与接口里记包坐标（一次 ABI bump，此时最便宜） |
| 验收 | ① 无清单项目 0 回归（现有套件/difftest 全绿）；② path 依赖跨目录编译通过；③ 手改清单后 `--locked` **失败**并打印 diff；④ 连续两次 `resolve` 输出**字节相同**；⑤ 项目整体移动目录后 lock **不变**（若有变化即为缺陷）；⑥ 仓库里没有绝对路径进锁 |
| 不做会怎样 | 后面每个阶段都要改锁格式，迁移成本叠乘；缓存键设计也要返工 |
| 解锁什么 | 「确定性输入」这一地基；后面所有阶段都建立在它上面 |
| 主要风险 | 触碰编译核心（module/driver/接口格式）→ 用 legacy 默认值隔离，ABI bump 一次付清 |

### 6.2 P1 · 内容寻址源 store + 离线

| 项 | 内容 |
|---|---|
| 目标 | 「包共用缓存」的第一半：**源码只存一份**，且可离线 |
| 交付 | (a) S1 store（§5.4.2 布局 + 原子写 + 只读权限）；(b) `fetch` 与 `--offline`；(c) 下载/读取时哈希校验；(d) `file://` 镜像；(e) `gc`（默认 dry-run）；(f) 项目侧不物化源码 |
| 验收 | ① `fetch` 后断网 `build` 成功；② 手工篡改 store 里一个字节 → **明确报错**而不是静默使用；③ 两个项目用同一包 → 磁盘只有一份（`du` 对比）；④ GC dry-run 列出条目且不删「在用/未过宽限期」的；⑤ 并发两个进程 fetch/build（复用 `tests/cache_race.sh` 思路）0 损坏 |
| 不做会怎样 | 每个项目/build 目录一份拷贝，磁盘与拉取时间双重浪费 |
| 解锁什么 | pnpm 式共享；内网离线；为 P3 的产物键提供「源码内容哈希」 |
| 主要风险 | store 的权限/共享语义；GC 与构建竞态（用 lease 解决） |

### 6.3 P2 · 注册表 + MVS 解析 + 别名

| 项 | 内容 |
|---|---|
| 目标 | 「包」真正存在：有人发布、有人解析、有人解释 |
| 交付 | (a) 注册表协议（元数据 + 源码 tarball；可先跑内部 file/HTTP 服务）；(b) MVS 解析器；(c) `update`（唯一写锁入口）；(d) 别名表（§5.3 R-3）；(e) `deps tree/why/explain`；(f) 冲突消息（§5.10.2） |
| 验收 | ① 造三包钻石（A→C>=1，B→C>=1.2）→ 选 1.2 且 explain 给见证；② 打乱注册表返回顺序/多镜像 → lock 字节不变；③ major 分叉 → 报错含两条要求与三种出路；④ `update` 只改指定包（其余行不动）；⑤ 同一清单在两台机器解出同一 lock |
| 不做会怎样 | 永远停在「本地路径依赖」，无法真正共享代码 |
| 解锁什么 | 包生态；人类可读的冲突诊断（这是回溯求解器最难做好的部分） |
| 主要风险 | 注册表运维与信任；建议**先内部跑**，把「发布流程 + 不可变存储 + 哈希校验」练熟再开放 |

### 6.4 P3 · 编译产物共享缓存

| 项 | 内容 |
|---|---|
| 目标 | 「包共用缓存」的第二半：**编译结果跨项目复用** |
| 交付 | (a) S3 store（键 = §5.4.3 的编译键）；(b) manifest 逐字段自检保留；(c) **补 target/ABI、编译器内容哈希**进键；(d) 读校验 + lease + GC 扩展；(e) 命中率统计（`--stats`）；(f) check 模式直接命中 S2 |
| 验收 | ① dep-heavy 项目二次构建明显加速（记录首次/二次耗时与命中率）；② **反向实验**：故意从键里漏掉一个开关 → 应观察到「切换开关仍命中」的错误行为，然后修复并留下回归测试（这条直接把 §5.4.3 的教训钉死）；③ 并发 2 进程同编 0 损坏；④ 复制项目到另一目录 → 命中（证明不依赖绝对路径）；⑤ 换编译器/换 target → 全 miss |
| 不做会怎样 | 依赖一多，每次构建都是全量编译；「包管理」只解决了取件没解决构建 |
| 解锁什么 | 大规模依赖下的可用构建速度；CI 缓存；为 P4 提供「产物按坐标复用」 |
| 主要风险 | 键漏项 = **静默错误结果**（比慢更糟）；必须用「漏项实验」验证而不是相信代码审阅 |

### 6.5 P4 · 显式多版本共存

| 项 | 内容 |
|---|---|
| 目标 | 让「渐进升级 / 插件」这类真实场景不被 major 分叉锁死 |
| 交付 | (a) 版本化 mangling + 单射编码（P0 已定规范，这里落地并验证）；(b) 接口/类型身份带包坐标；(c) 跨版本类型诊断（§5.10.2 第三条消息）；(d) 别名并存链接验证；(e) `deps tree` 标出别名 |
| 验收 | ① 同一程序两个 major 并存，运行结果正确；② 跨版本传值 → 编译错误且指出两个坐标；③ `nm` 可见两套符号；④ 缓存交叉复用 0 误命中；⑤ ASan 0 报告；⑥ 相对 P3，单版本场景的产物逐字节不变（mangling 在 P0 已版本化，P4 只加并存能力） |
| 不做会怎样 | major 升级只能「原子完成」，逼用户 fork/vendor（§5.3.3 理由 2） |
| 解锁什么 | 插件/渐进迁移；更健康的库演进生态 |
| 主要风险 | 一次性格式变更；**必须在 P3 的键设计里预埋版本**，否则 P4 要重做 P3 |

### 6.6 P5 · 治理（签名 / 透明日志 / SBOM / vendor 正式化 / 预编译产物）

| 项 | 内容 |
|---|---|
| 目标 | 让包管理能进内审/合规/大团队 |
| 交付 | (a) SBOM（SPDX/CycloneDX）；(b) 构建清单 + `rebuild-verify`；(c) vendor + `--check-vendor`；(d) 发布者签名/透明日志（可选）；(e) 预编译产物的**可选**分发（仅在 ABI/键故事清楚后） |
| 验收 | ① SBOM 能对锁生成并通过 schema 校验；② vendor 与锁不一致时明确报错；③ 篡改签名/内容能被拒绝且消息可诊断；④ 重建验证在干净机器上通过 |
| 不做会怎样 | 内审/合规场景不可用；大团队不敢用 |
| 解锁什么 | 企业/内网采用；供应链可审计 |
| 主要风险 | 过度设计；签名与预编译产物都是「等生态有了再说」的东西，不要提前做 |

### 6.7 阶段依赖与并行关系

| 关系 | 说明 |
|---|---|
| P0 → P1 | P1 的 store 键要用 P0 定下的「内容哈希 + 坐标」 |
| P1 → P2 | 无 store 的注册表会把项目变成「源码复制站」 |
| P0 + P2 → P3 | 产物键要用 P0 的坐标/版本 + P2 的依赖图 |
| P3 ⤳ P4 | P3 的键必须预埋版本维度 |
| P0–P4 都可独立验收 | 每阶段结束都能回答「做了什么、没做什么、下一阶段为什么」 |
| P5 可选/最晚 | 没有前四阶段，P5 是空转 |

**建议的第一个落点**：P0 的最小切片——**只有 path 依赖 + 锁 + ModuleMap + 版本进 mangling**。它不依赖注册表、不依赖 store、不改用户体验，但把后面所有阶段的地基（身份、锁、编译输入）一次定死。这也是整份文档里**最值得先拍板**的部分。

## 7. 开放问题（需要拍板）

## 附录 C 术语

| 术语 | 含义 |
|---|---|
| 包（package） | 分发的单位：一个坐标 + 一个版本 + 一棵源码树（可提供 1..N 个模块） |
| 模块（module） | import 的单位；有逻辑名、物理（mangled）名、接口文件 |
| 逻辑名 | 源码里 import 写的名字（如 json），可以被别名 |
| 物理名 / mangled 名 | 链接器看到的符号前缀（含包坐标与版本，如 pkg_json_1_4_0$json） |
| 坐标 | [registry/]namespace/name@version（§5.1.1） |
| 树哈希 | 对排序后的相对路径 + 文件内容算的 SHA-256；源码树的身份 |
| 编译键（compile key） | 决定一个模块 .o 内容的全部输入（§5.4.3）的哈希 |
| 模块解析表（ModuleMap） | 由锁派生、作为编译输入的「逻辑名 → 物理名 + 源码位置 + 坐标」映射 |
| 锁（lock） | 解析结果：全图 + 坐标 + 哈希 + 入边；构建期的唯一真相 |
| early cutoff | 依赖实现变但接口不变时，下游不必重编（靠接口哈希） |
| 别名（alias） | 清单里把某逻辑名绑定到另一个包坐标，用于显式多版本共存 |
| store | 全局内容寻址存储（源码 / 接口 / 产物三层） |
| lease | 构建对 store 条目的「占用声明」，防止 GC 删掉在用产物 |
| vendor | 把依赖源码复制进项目（离线/审计用），需一致性校验 |
